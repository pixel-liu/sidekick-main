# Code Review

找出当前审查范围内值得修复的问题，用具体位置、触发条件、错误机制和影响支持结论。遵守用户与仓库规定的审查范围和输出格式。审查请求本身不授权修改代码、提交、推送或在外部发布评论；用户同时要求修复时再按该范围执行。

## 确定范围和比较基准

先读仓库说明和相关接口约定，确认审查对象，区分工作区改动与已经提交的代码。根据对象取得证据：

| 审查对象 | 比较方式 |
| --- | --- |
| 当前改动 | 查看 Git 状态，同时检查暂存与未暂存 diff；按任务查看相关未跟踪文件，避免只审其中一部分 |
| 单次提交 | 用该提交的 diff 确认变更，合并提交要先确认要比较的父提交 |
| 分支 | 使用用户指定或仓库可确认的目标分支，并核对 merge-base 与 head；不随意假定目标是 main，也不把目标分支独有的变化算入被审改动 |
| PR | 核对 PR 的 base/head 提交及完整变更范围；缺少访问能力或内容时说明缺口，不把无关的本地 diff 当作该 PR |
| 文件或模块 | 按用户指定的行为和边界审查；没有变更比较基准时可以报告范围内已有缺陷，但不能声称由本次修改引入 |

有明确基准就继续工作，只对会实质改变审查范围的歧义补问。不能执行或读取某部分时说明覆盖限制。

对变更审查，先读 diff，再阅读必要的完整函数、调用方、接口实现、配置和测试；只查看修改行容易漏掉上下游行为。追踪到足以判断影响即可，不为每个小改动扫描全仓库。精确定位优先 `glob_files` / `grep_code` / `read_file`；只有语义线索时用 `search_code` 找候选入口，再用源码确认。

## 按改动选择检查维度

以下是问题线索，不要求每次逐项检查。优先评估改动影响最大的路径，按需扩大范围。

| 维度 | 检查重点 |
| --- | --- |
| 功能正确性 | 边界输入、空值、空集合、类型转换、分支与提前返回、操作顺序、失败后的状态和返回值；结合具体输入推演，关注错误值首次出现的位置 |
| 接口与兼容性 | 参数、返回值、异常、默认值、序列化格式、配置和命令行为是否改变；调用方、旧数据、其他实现和执行入口是否仍遵守同一契约 |
| 数据与持久化 | 多步写入的事务或原子替换、迁移、去重、删除、缓存一致性；检查失败、取消和进程退出是否留下半成品或丢失旧数据 |
| 并发与资源 | 共享可变状态、竞态、锁顺序和范围、异步结果归属；流、连接、线程池、子进程是否在成功、异常、取消、超时路径都正确收尾 |
| 安全与权限 | 从实际输入追踪到 Shell、SQL、文件路径等敏感操作；检查转义或参数化、路径与符号链接边界、权限和审批、敏感信息输出及项目/用户间隔离 |
| 性能与可靠性 | 循环内 I/O、重复扫描、无界读取/队列/线程、关键线程阻塞、重试放大及超时预算；用规模、调用频率或测量说明影响，不凭代码外观断定瓶颈 |
| 测试有效性 | 断言能否区分正确与错误行为，是否覆盖相关边界及失败路径；识别放宽断言、跳过测试和只复述实现的验证，已有测试通过不能证明未覆盖路径正确 |
| 变更完整性 | 新行为需要的配置、构建资源、注册、帮助和文档是否同步；仅在缺失会误导使用或导致功能不可用时作为缺陷，遵循仓库的明确要求 |

多个入口共享能力时，核对每条受影响路径是否一致，例如 Agent 不同执行模式是否共用正确的工具、上下文和取消逻辑。技术栈或业务专有约束从当前仓库获取，不将某个项目规则套用到所有项目。

## 将疑点核实为发现

对每个疑点，先建立“条件 → 调用/数据流 → 错误行为 → 影响”的因果链。检查调用方是否已经校验输入，外围是否已有锁、事务、权限检查、重试或清理，避免把局部看不到的保护当作不存在。

变更审查应比较修改前后，确认问题由改动引入、暴露或加重；原有且未受影响的问题不混入本次发现。全面模块审查可报告已有缺陷，并说明范围。不要假定未声明的业务要求或作者意图。

源码和明确契约足以证明的问题不强制运行。需要区分假设时，选择最小的现有测试、受控输入或只读检查，并确认执行条件；常规依赖解析遵循仓库流程。审查验证不应改写被审代码或测试；产生真实数据写入、外部操作或额外环境变更的实验需要相应授权。缺少必要环境时说明未验证部分，不把执行受阻当作代码缺陷。

测试报告必须说明实际执行的命令和结果，区分断言失败、环境失败、超时与跳过。没有运行就明确说明；静态证据仍可支持确定的缺陷，但不能编造复现结果。

以下情况不应直接作为确定发现：

- 缺乏触发条件、调用证据或明确契约，仅声称“可能有风险”；重要疑点单独标为待确认，并说明缺什么证据。
- 个人命名、排版、函数长度或抽象层次偏好；只有违反明确约定或产生具体维护/行为问题时才报告。
- 与本次范围无关的历史问题、理论性能优化，或用“缺少测试”代替尚未证明的功能缺陷。

同一个根因合并为一条发现，解释主要影响和必要的受影响位置，不按检查维度重复报告。不要为了凑数量降低证据标准；可操作的确定发现可以为零。

## 排序与交付

按实际影响和触发概率排序，仓库有等级定义时优先使用；否则参考：

- P0：无需特殊前提即可造成广泛、灾难性后果，需要立即阻止交付。
- P1：有可信触发路径的严重故障，如关键功能不可用、严重数据损坏或权限突破，应优先修复。
- P2：明确的功能、兼容性或可靠性缺陷，影响范围有限，应正常安排修复。
- P3：影响较小但确实值得修复的问题；不包含单纯个人偏好。

不要仅凭“安全”“并发”等类别给高等级，等级要与实际前提和后果一致。

除非用户规定其他格式，每条发现包含：

1. 简短标题，标注等级并指出具体错误。
2. 可核对的文件和行号，范围尽量小；变更审查优先指向实际引入问题的改动位置，必要时补充关联调用位置。
3. 用一段话说明触发条件、错误机制和实际影响，并给出关键源码、契约或已执行实验作为依据。
4. 有帮助时给出简短修复方向，不擅自展开重构或提交补丁。

先列确定发现，再单独说明必要的待确认项、审查范围和验证限制。未发现达到标准的问题时直接说明，不把“未发现”写成“保证没有缺陷”。检查完成且剩余疑点已有结论或清楚的证据缺口后结束，不无依据扩展到全量测试或全仓库审计。
