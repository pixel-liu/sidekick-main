# Skill Authoring

交付目标环境可发现、可完整加载且能指导实际任务的 skill。支持新建、从已有流程提炼、改进已有 skill。以用户当前要求为范围；只讨论方案时提供设计，不自行落盘，不主动挖掘历史会话或自动保存经验。

## 判断形式并确定目标

先读目标仓库说明，利用用户已提供的任务、示例、文档或现有 skill，明确要解决的问题、必要输入、预期交付、适用请求和完成标准。只有缺失信息会改变设计或位置时才补问，不要求重复提供已有信息。

- 多次复用、包含判断和工具选择的流程适合做 skill。
- 固定且需要确定性执行的机械步骤可用脚本；项目事实、构建命令和开发约定优先放在 `SideKick.md`，不复制成每个 skill 的通用规则。
- 从实例中提炼有依据的可复用方法，不把一次失败、单个项目的偏好或临时输入升级成普遍约束；不写入凭据或原始敏感会话。
- 更新已有 skill 时先读正文、资源及调用方式，围绕已观察到的问题修改，保留仍适用的用户定制；不要重新初始化或重写无关部分。

## 选择名称、位置和覆盖方式

名称使用小写字母、数字及单连字符，不以连字符开头或结尾，长度不超过 64 字符；目录名与 frontmatter 的 `name` 一致。用户指定名称需要规范化时说明最终名称，避免路径穿越或意外覆盖其他文件。

| 需求 | 位置与接入 |
| --- | --- |
| 当前项目使用，用户未另指定 | `.sidekick/skills/<name>/SKILL.md`，优先用项目内文件工具写入 |
| 用户明确要求跨项目使用 | `~/.sidekick/skills/<name>/SKILL.md`；先确认当前工具能访问该位置，不可访问时说明限制并提供完整内容与放置方法，不改路径围栏 |
| 用户明确要求随 SideKick 内置 | 在 SideKick 源码的 `src/main/resources/skills/<name>/` 创建资源，并登记 `SkillBuiltinExtractor`；执行目标仓库规定的测试与打包流程 |

先检查已发现的 skill 索引和目标目录；项目隐藏目录可直接用 `list_dir` / `read_file` 检查，不假定默认 glob 会搜索 `.sidekick`。同名优先级为项目 > 用户 > 内置，且整体覆盖而非逐字段合并。区分有意定制与名称碰撞；定制时保留完整必要指令及资源，避免生成残缺覆盖。

不直接编辑 `~/.sidekick/skills-cache/`。修改已有内置资源须按 `SkillBuiltinExtractor.CURRENT_VERSION` 约定升级缓存版本；新增独立 skill 目录可以独立解压，无需重建其他同版本缓存。不要为普通项目 skill 改内置清单或应用代码。

## 编写元数据与正文

文件以 UTF-8 编写，从首行 `---` 开始，用独占一行的 `---` 结束 frontmatter，并保留换行。至少填写非空 `name`、`description`；需要时加 `version`、`author`、`tags`。

SideKick 当前支持简单 `key: value`、`description: |` 缩进文本和行内数组 `tags: [a, b]`。不要依赖嵌套对象、YAML 锚点或复杂类型，也不假定其他平台的 UI 元数据、工具授权字段或初始化脚本在 SideKick 生效。

description 说明能力和可识别的触发请求，与相邻 skill 区分；只在容易误触发时说明排除范围。避免“所有开发任务”“随时加载”等过宽描述。

正文按任务复杂度组织，优先写能改变决策的信息：

- 必要输入、目标与边界；用户和目标仓库规则优先。
- 关键步骤中的判断依据、工具选择及替代路径；只引用当前环境存在的工具，缺少能力时说明可执行替代或缺口。
- 失败、信息不足、超时或条件不满足时如何调整，何时停止；不要求无条件重试或强制经过全部分支。
- 完成标准、必要验证和最终交付；简单任务允许短流程，不强制长报告。

避免空泛口号、复制通用常识、重复系统规则及把本次具体输入写死。skill 的任务说明不扩大用户授权；提交、推送和外部操作遵循用户要求及目标仓库规则，不自动添加确认流程。

## 正文预算与辅助资源

当前 `load_skill` 最多注入 5,120 个 Java 字符：以规范化换行后的正文 `String.length()`（UTF-16 代码单元）计数，不是 UTF-8 字节数；补充字符如部分 emoji 会占两个单位。按正文实际长度检查并留余量，不能靠运行时截断维持完整性。

核心决策和完成标准保持自包含。只有重复且确定性步骤才附 `scripts/`；只有确有必要的专项细节才附 `references/`，并写明何时读取及准确路径。引用文件不会随正文自动注入，内置或用户级目录可能在项目文件工具围栏外；不可达时保留必要指引在正文中，不假定相对链接会被自动解析。

不默认生成空目录、占位文件、额外 README 或 UI 配置。新脚本应在可用运行时中验证；需要未具备的依赖时说明，不声称已运行。更新时检查资源引用与使用方，避免删掉仍被依赖的文件。

## 最小完整示例

下面是项目级发布说明 skill 的示例，按实际任务替换用途和方法，不机械复制其工作流：

```markdown
---
name: release-notes
description: 根据用户指定的版本或提交范围整理面向使用者的发布说明，在用户要求撰写或更新发布说明时使用。
version: "1.0.0"
tags: [release, docs]
---

# Release Notes

确认发布基准和目标提交，阅读实际差异及仓库发布约定。范围已明确时直接继续，仅补问会改变输出的缺失信息。

按使用者可见的新增、修复和兼容性变化整理说明，合并重复内容，并为每项变化保留可核对的提交或文件依据。不把未交付计划写成已完成，不把实现细节当成用户收益。

交付发布说明与核对范围；证据缺失的项目标为待确认。仅撰写说明不自动创建 Release 或对外发布。
```

## 验证、接入与交付

先检查非空元数据、命名、支持的 YAML、正文长度、资源引用、真实工具名称和占位内容。目标环境有可用解析器或校验脚本时运行它，核对 warning；能容错加载不等于格式正确。不要假定 SideKick 自带某个外部平台的校验脚本。

再按实际复杂度挑选代表性请求，核对正常任务、缺少关键输入、执行失败及不相关请求的处理规则；关注误触发、过度执行、遗漏完成标准和越权动作。有条件时在隔离数据或临时项目实际执行相关路径，脚本验证与模型行为评测分别报告；只做静态场景走查时明确说明，格式通过不能证明行为正确。

项目或用户级文件写好后，说明在 SideKick 中运行 `/skill reload`，用 `/skill list` 和 `/skill show <name>` 核对有效来源、启用状态与内容；按需用 `/skill on <name>` 启用。slash 命令属于交互界面，不作为 Shell 命令执行。内置资源需构建并使用新程序重启解压，单独 reload 不能替代更新 JAR。若本会话已加载旧正文，使用新会话检验更新。

完成目标仓库要求的变更记录和交付步骤。交付文件位置、用途、触发示例、验证结果和限制；未实际检查运行时发现或加载时不得声称已生效。后续按真实误触发、遗漏或失败案例作针对性迭代，避免不断追加泛化禁令。
