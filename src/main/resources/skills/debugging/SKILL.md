# Debugging

围绕当前故障建立证据、验证原因、实施必要修复，并说明验证到什么程度。先遵守用户的任务范围和仓库说明；只要求诊断时交付诊断，不自行修改代码。

## 排查深度

- 对明确、局部且可验证的问题，直接完成“确认现象 → 定位原因 → 修复 → 验证”；不强制写计划、列多个假设或执行所有排查分支。
- 对原因不明、跨模块或偶发问题，维护简短的“已知事实 / 当前假设 / 下一项实验”，随新证据更新，不把猜测当结论。
- 优先利用已有堆栈、失败测试和日志。只补问会改变下一步排查的缺失信息，同时推进不依赖答案的检查。

## 建立基线并选择入口

先读仓库开发说明和相关构建配置，确认工作目录、启动或测试入口。若是 Git 仓库，查看当前分支、工作区改动及相关 diff，区分已有修改与本次排查产生的修改。

从现有证据中提取预期与实际行为、触发步骤或输入、关键错误、环境及复现频率；不要求用户重复提供已有信息。保留一条可对照的失败命令、失败断言或输入输出。复现应限定时间和影响范围；涉及真实数据改写、外部提交等副作用时，优先用隔离数据或已有测试，不因“排查”扩大授权。

| 已有线索 | 下一步 |
| --- | --- |
| 异常堆栈 | 阅读异常原因链，定位与故障相关的项目调用点，向上检查输入来源；异常抛出位置不一定是根因 |
| 失败测试 | 阅读失败断言、测试准备、被测实现和完整失败报告，区分断言失败、初始化失败与环境失败 |
| 错误文本、文件或符号 | 用 `grep_code` / `glob_files` 定位，再用 `read_file` 阅读相关范围及调用方 |
| 只有功能描述 | 用 `search_code` 辅助找到入口，再用源码和实际调用确认；语义搜索结果本身不是证据 |
| 曾经正常、现在失败 | 比较相关改动与环境差异；近期改动只是候选原因，不自动认定为根因 |

沿输入、配置、状态变化和返回值追踪到能解释现象的边界。按问题缩小阅读范围，不为了全面扫描整个仓库。无法复现时记录尝试条件，继续做证据支持的静态排查，并标明尚未复现。

## 用实验区分原因

选择最有证据且验证成本低的假设，说明依据、最小实验以及什么结果支持或否定它。原因已明确时无需额外制造假设。

实验尽量只改变一个关键条件，记录命令或操作、关键结果与对假设的影响。可使用小范围测试、受控输入、临时诊断日志或已有调试工具；临时日志只记录必要信息，不输出凭据、完整环境变量或真实敏感数据，交付前清理无用探针。

结果否定假设就更新方向；同样的尝试没有产生新信息时，不盲目重试或连续试改。仅在有瞬态故障证据时做有界重试。工具超时不等于目标程序卡死，应检查工具时间限制、子进程及可用日志。

按线索选用以下分支，不逐项机械执行：

| 故障类型 | 有区分力的检查 |
| --- | --- |
| 构建或依赖失败 | 识别首个实质错误，核对工具链版本、依赖解析及构建参数；区分下载失败、编译失败和测试失败，避免先清空全部缓存或升级所有依赖 |
| 运行异常或结果错误 | 检查边界输入、类型转换、配置优先级、状态更新和异常传播，用具体输入追踪错误值首次出现的位置 |
| 偶发或并发失败 | 对比通过与失败条件，检查共享状态、执行顺序、锁及资源生命周期；优先用可控同步复现，不靠增加 sleep 掩盖竞态 |
| 卡死、超时或性能退化 | 使用相同工作负载对比基线，区分启动、计算、锁等待、I/O 和外部服务耗时；已有工具可用时再采集线程栈或性能数据，不凭代码外观判断瓶颈 |
| 配置、MCP 或服务集成失败 | 按有效配置来源、进程或连接、握手、能力发现、实际调用逐层定位；区分权限、协议、参数与业务响应，检查凭据是否生效但不展示其值 |

## 修复与验证

修改前应能说明“什么条件经由什么机制导致当前失败”，并有源码、失败用例或实验支持。证据不足时可提出候选修复，但不能声称已确认根因。

优先修改导致故障的必要范围，检查相关调用方与行为兼容性。不要夹带无关重构、覆盖用户已有修改，或直接回滚整个工作区。若代码本来符合约定而环境不符，应修正必要的环境或配置，不强行修改业务逻辑。

吞异常、放宽断言、禁用校验、随意延长超时或增加重试不能单凭“错误消失”作为修复依据。确需临时缓解时说明适用条件、残余问题与后续根因验证。

验证按以下顺序选择必要范围：

1. 重跑原失败用例或复现步骤，核对预期结果；测试通过但未覆盖原故障时，不能据此宣布修复。
2. 对适合自动化且能防止复发的缺陷补充回归测试，条件允许时确认它能在修复前失败、修复后通过；避免只复述实现的测试。
3. 运行相关边界和受影响调用方的检查。使用仓库规定的命令，确认测试实际执行；构建成功或跳过测试不能算测试通过。
4. 偶发问题记录复现条件与重复验证次数；性能问题在可比较的工作负载下报告前后测量，不以一次未复现或一次变快证明消除。

若新修改或失败暴露了更广影响，再扩大验证。已有相关检查通过后，不无依据反复跑全量测试。完成仓库要求的变更记录和交付步骤，但 skill 本身不额外授予提交、推送或外部操作权限。

## 完成判断与交付

- 已定位：证据足以解释故障，但修复尚未完成或尚未验证。
- 已缓解：症状得到控制，根因或触发条件仍可能存在。
- 已修复并验证：必要修改完成，原失败路径及相关检查通过；结论限定在实际验证范围内。
- 尚未确认或受阻：说明缺失的证据、环境或权限，给出最小下一步；不要把未执行、超时或无法复现写成通过。

一旦原问题和必要回归已验证，就结束排查。若剩余步骤依赖不可用的环境或用户信息，交付现有证据和具体缺口，不无限尝试。

最终简洁说明：问题表现；根因及关键证据（文件位置、错误或实验）；修改或缓解内容；实际执行的验证及结果；剩余限制和下一步。简单问题用一段话即可，不强制套用完整报告模板。
