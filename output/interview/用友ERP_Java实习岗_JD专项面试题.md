## 二、Java 基础高频题

### 6. `==` 和 `equals()` 有什么区别？为什么重写 equals 还要重写 hashCode？

**参考答案：**

基本类型使用 `==` 比较值；引用类型使用 `==` 比较是否指向同一个对象。`equals()` 默认行为也是比较引用，但 String 等类重写后会比较业务内容。

HashMap 和 HashSet 先根据 hashCode 定位桶，再通过 equals 判断是否为同一个逻辑对象。若两个对象 equals 为 true，但 hashCode 不同，它们可能进入不同桶，导致查找失败或 Set 出现逻辑重复。因此规范要求 equals 相等的对象必须有相同 hashCode。作为 key 的字段还应尽量不可变，否则放入 Map 后修改字段会导致无法查回。

### 7. String、StringBuilder 和 StringBuffer 有什么区别？

**参考答案：**

String 不可变，每次看似修改通常产生新对象，适合作为常量、参数和 Map key。StringBuilder 可变且不保证线程安全，单线程大量拼接时优先使用。StringBuffer 的主要方法带同步，线程安全但通常开销更高。

循环拼接 SQL 或日志时可以使用 StringBuilder，但实际 SQL 更应该使用预编译参数而不是直接拼接用户输入。编译器会优化简单的字符串常量连接，但循环中的动态拼接仍应避免反复创建 String。

### 8. ArrayList 和 LinkedList 如何选择？

**参考答案：**

ArrayList 底层是连续数组，随机访问 O(1)，尾部追加摊销 O(1)，CPU 缓存友好，通常是默认选择。中间插入删除需要移动元素，但真实业务中它经常仍比 LinkedList 更快。

LinkedList 是双向链表，通过下标访问 O(n)，每个节点还有额外对象和指针开销。只有已经拿到节点位置并频繁在附近插入删除时才可能有优势。队列场景一般优先 ArrayDeque，而不是 LinkedList。

### 9. HashMap 的 put 流程是什么？

**参考答案：**

先计算 key 的 hash 并扰动，根据数组长度定位桶。桶为空时直接插入；桶不为空时比较 hash 和 equals，找到相同 key 就覆盖，否则追加到链表或红黑树。Java 8 中桶节点较多并且数组容量达到要求时会树化。

插入后如果元素数超过 `容量 × 负载因子`，HashMap 会扩容并重新分配节点。默认负载因子 0.75 是空间和查询效率的折中。HashMap 不是线程安全的，并发写要使用 ConcurrentHashMap 或在更高层控制并发。

### 10. 接口和抽象类有什么区别？你的项目里为什么使用接口？

**参考答案：**

接口主要定义能力契约，类可以实现多个接口；抽象类可以保存状态、构造逻辑和公共实现，但只能单继承。接口适合解耦调用方与实现，抽象类适合多个实现共享大量稳定代码。

Sidekick 中 `LlmClient` 定义统一模型能力，Agent 只依赖接口；多个 OpenAI-compatible 模型又继承公共抽象类复用 HTTP 和 SSE 解析。这是接口加模板基类的组合：接口保证可替换性，抽象类减少重复代码。

### 11. checked exception 与 runtime exception 应该怎么处理？

**参考答案：**

checked exception 通常代表调用者能够感知和处理的外部失败，例如 IOException；runtime exception 常用于参数错误、非法状态或统一业务异常。选择重点不是语法，而是调用方能否恢复以及是否需要强制处理。

接口层可以将底层异常转为明确的业务错误码，但日志中要保留原始堆栈。不能 `catch (Exception)` 后返回成功或空值，也不能把数据库详情直接返回前端。事务方法如果捕获异常后不再抛出，还可能导致事务错误提交。

### 12. 什么是深拷贝和浅拷贝？ERP 单据复制时要注意什么？

**参考答案：**

浅拷贝只复制对象本身，内部引用仍指向原对象；深拷贝会复制需要独立变化的内部对象。ERP 单据通常包含主表、明细行、附件和关联关系，不能简单复制引用。

复制单据时还要重新生成主键和单据号，重置审批状态、创建人和时间，判断哪些业务字段允许继承，并重新建立明细外键。附件、来源单据关系和金额字段是否复制必须由业务规则决定。

### 13. Stream API 有什么优缺点？什么时候不建议使用？

**参考答案：**

Stream 适合表达过滤、映射、分组和聚合，能够减少样板循环代码。例如把订单按客户分组后汇总金额。它强调声明式处理，默认不修改原集合。

如果链路包含复杂状态、异常处理、调试步骤或大量副作用，普通循环可能更清楚。`parallelStream()` 也不能随意使用，它依赖公共 ForkJoinPool，任务粒度小或存在阻塞 IO 时可能更慢，还会带来线程安全和上下文传播问题。

## 三、SQL 与业务数据处理重点题

假设存在以下简化表：

```sql
customer(id, name, organization_id)
sales_order(id, customer_id, order_no, order_date, amount, status)
sales_order_item(id, order_id, product_id, quantity, unit_price)
product(id, product_name, category_id)
inventory(product_id, warehouse_id, quantity, version)
```

### 14. 查询每个客户已审核订单的总金额，并按金额从高到低排序。

**参考答案：**

```sql
SELECT c.id,
       c.name,
       COALESCE(SUM(o.amount), 0) AS total_amount
FROM customer c
LEFT JOIN sales_order o
       ON o.customer_id = c.id
      AND o.status = 'APPROVED'
GROUP BY c.id, c.name
ORDER BY total_amount DESC;
```

把状态条件写在 `ON` 中可以保留没有已审核订单的客户；若写进 `WHERE`，LEFT JOIN 会被过滤得接近 INNER JOIN。`COALESCE` 把没有订单时的 null 转成 0。

### 15. 查询最近 30 天内订单金额最高的 10 个客户。

**参考答案：**

```sql
SELECT c.id,
       c.name,
       SUM(o.amount) AS total_amount
FROM sales_order o
JOIN customer c ON c.id = o.customer_id
WHERE o.order_date >= CURRENT_DATE - INTERVAL 30 DAY
  AND o.status = 'APPROVED'
GROUP BY c.id, c.name
ORDER BY total_amount DESC
LIMIT 10;
```

索引可考虑 `(status, order_date, customer_id)`，但顺序应根据字段选择性和主要查询模式验证。必须通过 EXPLAIN 看扫描行数、访问类型和是否出现临时表，而不是只凭规则判断。

### 16. 如何找出重复的订单号？

**参考答案：**

```sql
SELECT order_no, COUNT(*) AS duplicate_count
FROM sales_order
GROUP BY order_no
HAVING COUNT(*) > 1;
```

`WHERE` 在分组前过滤行，`HAVING` 在分组后过滤聚合结果。发现重复后不能直接删除，要先确认保留规则、外键引用和审计要求。业务上如果订单号必须唯一，应增加唯一索引，从源头阻止并发重复写入。

### 17. WHERE 和 HAVING 有什么区别？

**参考答案：**

WHERE 在分组前过滤原始行，不能直接使用聚合结果；HAVING 在 GROUP BY 后过滤分组。能放 WHERE 的普通条件应尽量放 WHERE，先减少参与聚合的数据量。

例如查询总金额大于 1 万的客户，订单状态放 WHERE，总金额条件放 HAVING：

```sql
SELECT customer_id, SUM(amount) total
FROM sales_order
WHERE status = 'APPROVED'
GROUP BY customer_id
HAVING SUM(amount) > 10000;
```

### 18. INNER JOIN 和 LEFT JOIN 的区别是什么？

**参考答案：**

INNER JOIN 只返回两边能够匹配的数据；LEFT JOIN 保留左表所有行，右表无匹配时相关列为 null。是否使用 LEFT JOIN 取决于业务是否要保留“没有明细”的主体。

使用 LEFT JOIN 时要特别注意右表过滤条件的位置。放在 ON 中影响匹配但保留左表；放在 WHERE 中会过滤掉右表为 null 的行。ERP 报表中这是常见的数据遗漏原因。

### 19. 如何查询每个类别销售额最高的前三个商品？

**参考答案：**

MySQL 8 可以使用窗口函数：

```sql
WITH product_sales AS (
    SELECT p.category_id,
           p.id AS product_id,
           p.product_name,
           SUM(i.quantity * i.unit_price) AS sales_amount
    FROM sales_order_item i
    JOIN sales_order o ON o.id = i.order_id
    JOIN product p ON p.id = i.product_id
    WHERE o.status = 'APPROVED'
    GROUP BY p.category_id, p.id, p.product_name
), ranked AS (
    SELECT *,
           ROW_NUMBER() OVER (
               PARTITION BY category_id
               ORDER BY sales_amount DESC
           ) AS rn
    FROM product_sales
)
SELECT category_id, product_id, product_name, sales_amount
FROM ranked
WHERE rn <= 3;
```

如果并列金额都要保留，可以使用 `DENSE_RANK()`。回答时要说明 MySQL 版本，因为旧版本不支持窗口函数。

### 20. 一条 SQL 很慢，你会怎样排查？

**参考答案：**

先获取完整 SQL、参数和慢发生的时间，使用 EXPLAIN 或 EXPLAIN ANALYZE 查看访问类型、预估与实际行数、索引选择、回表、排序和临时表。然后检查表规模、数据分布、统计信息、锁等待以及数据库整体负载。

优化可能包括改写查询、建立合适联合索引、减少返回列、分页、先过滤再关联或拆分大事务。不能看到全表扫描就机械加索引，因为小表或返回比例很高时全表扫描可能更合理。修改后要在接近真实的数据量上对比执行计划和耗时。

### 21. 什么是覆盖索引和索引下推？

**参考答案：**

覆盖索引是查询需要的字段都在索引中，存储引擎无需再根据主键回表。例如联合索引 `(customer_id, status, amount)` 可以覆盖只查询这几个字段的部分语句。

索引条件下推是存储引擎在扫描索引时尽早判断索引中的条件，减少回表数量。它们都能降低 IO，但过宽索引会增加磁盘和写入成本，所以应根据高频查询选择，而不是把所有字段都加入索引。

### 22. MySQL 可重复读是怎么实现的？什么是快照读和当前读？

**参考答案：**

InnoDB 使用 MVCC、undo log 和 Read View 实现快照读。普通 SELECT 通常读取符合当前 Read View 可见性规则的历史版本，因此同一事务内多次读取可以保持一致。

`SELECT ... FOR UPDATE`、UPDATE 和 DELETE 属于当前读，读取最新版本并加锁。可重复读并不意味着所有场景都不加锁；涉及库存扣减等需要基于最新值做修改的场景，应使用条件更新、当前读或乐观锁。

### 23. 两个请求同时扣减库存，如何避免超卖？

**参考答案：**

可以使用一条带条件的原子 SQL：

```sql
UPDATE inventory
SET quantity = quantity - :count
WHERE product_id = :productId
  AND warehouse_id = :warehouseId
  AND quantity >= :count;
```

然后检查受影响行数，等于 1 表示成功，等于 0 表示库存不足或记录不存在。这样避免“先查库存、再更新”之间的并发窗口。

也可以使用 version 字段做乐观锁，冲突后有限重试；悲观锁适合竞争较小且事务很短的场景。无论哪种方式，都应配合订单幂等键，防止相同请求重复扣减。

### 24. SQL 注入是怎么产生的？如何防止？

**参考答案：**

SQL 注入通常来自把用户输入直接拼接进 SQL，使输入被当作 SQL 结构执行。应使用 PreparedStatement 或 MyBatis `#{}` 参数绑定，而不是 `${}` 拼接。

动态排序字段、表名等无法通过普通参数绑定的部分，应使用服务端白名单映射，不能直接接受客户端字符串。数据库账号还要遵循最小权限，对输入做业务校验，并避免把 SQL 错误详情返回用户。

### 25. 执行数据修复 SQL 前，你会做哪些检查？

**参考答案：**

先明确修复范围、业务规则和回滚方式，在只读查询中确认预计影响行数，并让业务或负责人确认样本。更新语句必须有精确 WHERE 条件，优先使用主键或临时表限定范围。

在测试环境验证后，生产执行前备份目标数据或生成反向 SQL，开启事务时确认数据量和锁影响。先 SELECT，再执行 UPDATE，再检查影响行数和业务结果，最后决定提交。大批量修复要分批执行，避免长事务、主从延迟和大范围锁等待。整个过程保留脚本、审批和结果记录。

## 四、Spring Boot 与接口开发

### 26. 一个标准的 Spring Boot 接口应如何分层？

**参考答案：**

Controller 负责 HTTP 参数接收、校验和响应转换；Service 负责业务规则和事务；Repository/Mapper 负责持久化。DTO 用于接口输入输出，Entity 对应数据库模型，不应直接把 Entity 暴露给外部。

分层不是为了增加文件数量，而是隔离职责。简单查询可以保持简洁，但订单审核、库存变化等核心逻辑必须放在服务层，避免散落在 Controller 或 SQL 中。异常通过统一处理器转换为标准错误响应。

### 27. 请设计一个“根据订单号查询订单详情”的 REST 接口。

**参考答案：**

可以设计为：

```http
GET /api/v1/sales-orders/{orderNo}
Authorization: Bearer <token>
```

返回订单头、明细和必要的状态信息。Controller 校验路径参数，Service 先根据当前用户解析组织和数据权限，再查询订单及明细。不存在返回 404，无权限返回 403，参数错误返回 400，系统异常返回统一 500 错误码。

如果订单号不是全局唯一，URL 或查询条件中还要包含租户/组织，但租户身份不能只信任客户端参数，应从认证上下文获取。接口文档需要说明字段含义、状态枚举、示例和错误码。

### 28. POST、PUT、PATCH 有什么区别？接口如何保证幂等？

**参考答案：**

POST 通常用于创建或执行动作，默认不保证幂等；PUT 表示对指定资源进行完整替换，语义上幂等；PATCH 表示局部修改，是否幂等取决于操作定义。

创建订单等接口可以要求客户端发送幂等键，服务端建立唯一约束并保存首次处理结果。重复请求返回同一业务结果，而不是再次创建或扣库存。仅依赖前端按钮禁用不能保证幂等，因为网络重试、网关重放和用户多端操作都可能造成重复请求。

### 29. `@Valid` 能解决什么问题？业务校验应该放在哪里？

**参考答案：**

`@Valid` 配合 Bean Validation 适合校验非空、长度、格式、数值范围等结构性规则，例如订单号不能为空、数量必须大于零。Controller 参数校验失败后由统一异常处理器返回字段级错误。

“订单当前状态是否允许审核”“库存是否充足”等依赖数据库和业务上下文的规则应放在 Service。数据库仍需唯一索引、非空和外键等约束作为最后防线。三层校验分别改善用户体验、保证业务规则和保护数据一致性。

### 30. Spring 的 `@Transactional` 为什么可能不生效？

**参考答案：**

常见原因包括同类内部调用绕过代理、方法不是可代理的 public 方法、对象不是 Spring 容器管理的 Bean、异常被捕获后未抛出，以及异常类型不符合默认回滚规则。

事务只管理对应数据库资源，不能自动覆盖远程接口、Redis 或消息队列。ERP 中“保存订单并调用外部系统”不能认为加一个注解就全部原子，需要幂等、状态机、Outbox 或补偿机制。

### 31. 如何设计统一响应和全局异常处理？

**参考答案：**

可以定义包含业务码、消息、数据和 traceId 的响应结构，通过 `@RestControllerAdvice` 处理参数校验异常、业务异常和未知异常。业务异常返回稳定错误码，前端据此展示或处理；未知异常对外返回通用信息，对内记录完整堆栈。

HTTP 状态码也应有语义，不能所有情况都返回 200。日志中通过 traceId 关联上下游，但不能打印密码、Token、身份证号和完整财务数据。

### 32. 接口联调时对方说“你接口有问题”，你怎么处理？

**参考答案：**

我会先收集可复现信息：环境、URL、请求时间、traceId、请求方法、Headers、参数、响应状态和响应体。然后用 Postman/curl 按接口文档独立复现，确认问题出在请求格式、鉴权、网关、服务代码、数据库还是下游系统。

沟通时不先争论归属，而是共享脱敏的请求和日志证据。如果文档与实现不一致，立即确认正确契约并同步修改。修复后提供可验证样例，并记录根因和回归范围。

### 33. 前端调用接口出现跨域问题是什么原因？怎么解决？

**参考答案：**

浏览器同源策略限制不同协议、域名或端口间的请求。复杂请求可能先发送 OPTIONS 预检，服务端或网关若未正确返回允许的 Origin、Method、Header，就会被浏览器拦截。

通常在 Gateway 或后端统一配置 CORS，明确允许的来源和方法。携带 Cookie 时不能使用通配 Origin，还需要正确配置 credentials。不能简单建议关闭浏览器安全策略，那只适合临时本地验证，不能作为生产方案。

## 五、Bug 排查与接口联调场景题

### 34. 线上用户反馈“订单保存成功，但列表里看不到”，你怎么排查？

**参考答案：**

先确认保存接口是否真的成功，包括返回业务码、数据库是否提交、订单的租户、组织、状态和逻辑删除字段。然后检查列表查询的过滤条件、数据权限、缓存和读写分离延迟。

如果数据库存在但列表没有，重点比较保存数据与查询条件；如果数据库不存在，要检查事务回滚、异常是否被吞掉和连接的数据源。最后用同一用户和同一请求复现，并补充覆盖权限、状态和事务的回归测试。

### 35. 接口偶发 500，但本地无法复现，怎么办？

**参考答案：**

通过时间、用户和 traceId 找到完整调用链，检查异常堆栈、输入参数摘要、版本、实例和下游耗时。偶发问题常与并发、脏数据、超时、连接池、缓存和特定实例有关。

对比成功与失败请求的差异，必要时在测试环境构造相同数据和并发条件。不能为了方便把生产完整数据复制到本地，也不能只通过重启掩盖问题。修复后增加针对根因的测试和监控告警。

### 36. 出现 NullPointerException，你会怎么定位，而不是到处加判空？

**参考答案：**

首先根据堆栈定位准确行号，识别哪个对象为 null，再追踪它为什么违反预期：参数缺失、查询无结果、映射错误、并发状态变化还是旧数据不完整。

如果 null 合法，应在边界明确处理，例如返回 Optional、404 或默认值；如果 null 不应该出现，应在创建和持久化阶段建立约束并尽早失败。到处加判空可能把问题延迟成更难理解的数据错误。

### 37. 修改一个线上 Bug 前，怎样控制影响范围？

**参考答案：**

先写出最小复现，明确预期与实际结果，找到根因而不是只修表现。阅读调用方、数据结构和相关测试，评估是否影响其他单据状态、权限和接口。

修改保持最小，补回归测试和必要的数据兼容；通过代码评审和测试环境验证。高风险改动使用开关或灰度发布，并准备回滚方案。上线后观察相关错误率、日志和业务指标。

### 38. 后端接口返回正常，但前端页面展示错误，如何判断问题在哪一侧？

**参考答案：**

使用浏览器 Network 查看真实请求和响应，与接口文档对比字段名、类型、空值、时间格式和状态枚举。如果响应正确，再检查前端数据转换、组件绑定和缓存；如果响应已错误，则根据 traceId 查后端。

还要注意“HTTP 200”不代表业务成功，有些系统把业务错误放在响应码字段里。最有效的联调方式是双方基于同一个请求样例和契约定位，而不是互相截图猜测。

### 39. 测试环境正常，生产环境失败，常见原因有哪些？

**参考答案：**

常见差异包括配置、数据库版本和数据量、权限、网络白名单、时区、字符集、依赖服务地址、环境变量和发布包版本。生产并发和真实脏数据也可能触发测试环境没有覆盖的问题。

排查时先对比配置和版本指纹，再看实际请求、日志与依赖状态。不能直接登录生产修改代码或数据；任何临时修复都要经过审批、留痕并同步回正常发布流程。

### 40. 如何写一份有价值的 Bug 修复记录？

**参考答案：**

至少包含问题现象、影响范围、复现步骤、期望结果、实际结果、环境和版本、根因、修改内容、测试用例、数据修复、发布与回滚方式。如果有截图或日志，应脱敏并附 traceId 和关键时间点。

记录的目标不是证明“我修过”，而是让其他人能够复现、评审和避免再次发生。根因和预防措施比单纯粘贴代码更重要。

## 六、Git、测试和团队协作

### 41. Git 中 add、commit、push 分别做什么？

**参考答案：**

`git add` 把工作区选择的修改放入暂存区；`git commit` 把暂存内容生成本地提交；`git push` 把本地提交发送到远程仓库。提交前应查看 status 和 diff，避免把配置密钥、IDE 文件或无关改动提交进去。

一个提交应围绕一个清晰目的，提交信息说明“为什么改”，而不只是“update”。

### 42. merge 和 rebase 有什么区别？团队中如何使用？

**参考答案：**

merge 把两个分支历史合并，保留真实分叉并生成合并提交；rebase 把当前分支提交重新放到新基线之上，使历史线性，但会改写提交 ID。

个人尚未共享的功能分支可以 rebase 更新基线；已经多人共享的公共分支不要随意 rebase 和强推。最终遵循团队规范，不以个人偏好破坏历史。

### 43. 提交代码时发生冲突，你如何处理？

**参考答案：**

先更新目标分支并理解双方改动目的，再逐个文件处理冲突，不能直接选择“全部使用我的”。解决后编译并运行相关测试，检查 diff，确认没有丢失对方逻辑，再完成 merge 或 rebase。

如果冲突涉及不熟悉的业务规则，应找原作者确认。减少大提交、及时同步和明确模块边界可以降低冲突概率。

### 44. 单元测试、集成测试和接口测试有什么区别？

**参考答案：**

单元测试验证一个类或方法的确定性逻辑，依赖通常用 Fake 或 Mock；集成测试验证数据库、Spring 容器、消息或多个组件协作；接口测试从 HTTP 层验证参数、鉴权、响应和异常。

对于订单接口，单元测试可覆盖状态转换，集成测试验证事务和 SQL，接口测试覆盖权限、错误码和序列化。测试重点应包括边界和失败路径，而不只是正常流程。

### 45. 接到需求后，你会输出哪些文档或记录？

**参考答案：**

小需求至少记录需求理解、影响范围、接口或数据变化、测试结果和发布注意事项。接口变更更新接口文档和示例；数据库变更提供正向、校验和回滚脚本；Bug 提供复现与根因；版本发布记录变更项、依赖、配置和回滚方案。

文档应与代码在同一次变更中更新，避免上线后再补。内容以团队成员能够复现和接手为标准，而不是追求篇幅。

## 七、ERP、财务与供应链业务题

### 46. 你怎么理解 ERP 中的“单据”和“单据状态”？

**参考答案：**

单据是业务过程的结构化载体，通常包含单据头和多条明细，例如销售订单、采购订单、入库单和发票。它不仅是一条数据库记录，还连接审批、库存、应收应付和后续单据。

状态常包括草稿、提交、审核、驳回、关闭等，状态转换必须由明确业务动作触发。修改和删除权限通常与状态有关，已审核单据不能随意直接更新。设计时应使用状态机思维，校验当前状态和目标状态，记录操作人、时间和审批轨迹。

### 47. 销售订单到回款的大致流程是什么？

**参考答案：**

简化流程是客户下单、销售订单审核、出库、确认应收、开票、收款和核销。不同企业的先后关系可能不同，例如先款后货或先开票后收款。

系统中各环节可能产生不同单据，并存在数量、金额和来源关系。二次开发不能只修改销售订单表，还要确认是否影响库存、应收、发票和报表。面试中如果不确定企业具体流程，应先说明这是通用理解，再询问该公司的实际规则。

### 48. 采购到付款的大致流程是什么？

**参考答案：**

常见流程是采购申请、采购订单、到货或入库、供应商发票、应付确认、付款和核销。核心控制包括供应商、价格、数量、收货、发票与付款之间的匹配。

例如三单匹配会比较采购订单、收货记录和发票，差异超过规则时需要审批。系统修改采购数据时，要考虑库存和应付模块的联动，不能只从页面字段理解需求。

### 49. 什么是借贷记账法？不了解财务时应该怎么回答？

**参考答案：**

借贷是会计记账方向，不简单等于增加或减少。每笔业务至少涉及两个账户，借方金额与贷方金额相等。资产类科目通常借增贷减，负债和所有者权益通常贷增借减，收入和费用也有相应规则。

作为开发实习生，我需要理解业务单据如何生成凭证、期间和科目如何影响记账，但具体会计政策必须与财务顾问或产品确认。我不会在不理解规则时直接修改凭证数据，而会通过业务样例和验收口径确认。

### 50. ERP 数据为什么特别强调组织和权限？

**参考答案：**

集团可能包含多个公司、部门、仓库和账套。同一个用户可以操作某些组织但不能访问其他组织的订单、工资或财务数据。权限不仅是菜单是否可见，还包括数据行、字段、操作和单据状态。

后端查询必须主动加入组织和租户条件，不能只靠前端传 organizationId。导出、打印、附件下载和接口也要做同样校验。缓存 key、日志和批处理同样要带作用域，否则可能发生跨组织数据泄露。

## 八、综合与 HR 场景题

### 51. 你能否保证连续实习 6 个月？如何安排学业？

**参考答案：**

必须按真实情况回答。如果能够保证，可以明确可到岗日期、每周出勤天数、预计结束时间以及课程安排。例如：“我可以从某日开始全职实习至少 6 个月，学校课程已经集中安排，毕业设计可以在业余时间推进。如遇必须返校事项，我会提前沟通。”

不要只回答“可以”，招聘方更关心时间是否稳定以及是否存在突然离岗风险。

### 52. 产品临时提出一个紧急需求，但描述不清，你怎么办？

**参考答案：**

先确认紧急原因、上线时间、目标用户和最小验收范围，再用流程、字段和示例把歧义具体化。对于无法及时确认的部分，明确假设并获得产品或负责人认可。

把需求拆成必须上线和可后续补充两部分，评估风险与回滚方案。不能因为“紧急”就跳过数据权限、测试和评审；可以缩小范围，但不能隐藏风险。

### 53. 你提交的代码被评审指出很多问题，你如何处理？

**参考答案：**

先区分必须修复的问题、团队规范和可讨论的设计选择，逐条理解原因并修改。对不理解的意见，我会带着具体代码和方案询问，而不是机械照改或情绪化争辩。

修改后回复处理结果，补充测试，并把重复出现的问题整理到个人检查清单。代码评审的目标是提高代码和团队知识共享，不是评价个人能力。

### 54. 同时有两个任务，一个功能开发、一个线上 Bug，你怎么排优先级？

**参考答案：**

先根据影响范围、严重程度、是否阻塞业务、是否有临时绕过方案和截止时间判断。影响生产核心流程或数据正确性的 Bug 通常优先，并及时向两边负责人同步调整。

如果 Bug 可以快速止损，先通过回滚、开关或降级恢复服务，再分析根因；功能任务保留当前进度和下一步，避免切换后丢失上下文。最终优先级由团队业务目标决定，不应仅凭个人喜好。

### 55. 你有什么问题想问面试官？

**参考答案：**

可以选择三到四个有价值的问题：

1. 实习生入职后主要参与用友哪个产品和业务模块？
2. 二次开发以 Java 代码、平台扩展还是报表和接口为主？
3. 团队目前的开发、测试、发布和代码评审流程是什么？
4. 对实习生前三个月的主要考核目标是什么？
5. 是否有导师或业务培训，财务和供应链知识如何学习？

不建议第一轮只询问能否摸鱼、频繁请假或很快转岗，也不要问 JD 中已经写得很清楚的内容。
