## 一、开场、自我介绍与项目总览

第一个项目是 Sidekick，它是一个用 Java 17 编写的终端 AI 编程 Agent。我实现了 ReAct、Plan-and-Execute 和 Multi-Agent 三种执行模式，并围绕它构建了工具调用、MCP、短期与长期记忆、代码 RAG、浏览器访问、人工审批和快照回滚等能力。这个项目让我深入理解了如何把大模型的不确定输出变成一个可控制、可观测、可恢复的软件执行流程。

第二个项目是 IntelliDoc，它是一个基于 Spring Boot 的企业知识库系统。我围绕文档异步处理、分片上传、Elasticsearch 混合检索、组织级 RBAC、LLM 流式问答和降级机制进行了设计。相比只调用模型接口，我更关注后端系统中的可靠性、一致性、权限和用户体验。我希望在实习中继续提高工程能力，并参与真实业务系统的开发与优化。

### 2. 你的两个项目分别解决了什么问题？它们最大的区别是什么？

**参考答案：**

Sidekick 解决的是“如何让大模型在本地代码仓库中安全、持续地完成开发任务”。它的核心不是一次问答，而是模型根据上下文决定调用文件、命令、代码搜索、浏览器或 MCP 工具，得到结果后继续推理，直到任务完成。它更偏 Agent Runtime 和开发工具。

IntelliDoc 解决的是“企业文档如何被安全地处理、检索和用于问答”。核心链路是文档上传、异步解析、切片、向量化、索引、权限过滤、混合召回、重排和流式生成，更偏企业后端与 RAG 平台。

二者共同点是都需要管理上下文、检索外部知识、调用 LLM 并处理失败；区别是 Sidekick 的输出会触发真实工具操作，因此更强调执行安全和状态恢复，而 IntelliDoc 更强调文档处理吞吐、检索质量、租户权限与服务稳定性。

### 3. 为什么选择独立开发，而不是直接使用 LangChain 或 Spring AI？

**参考答案：**

我希望真正理解 Agent 的运行机制，所以核心链路没有交给框架黑盒处理，而是自己抽象了 `LlmClient`、消息、工具定义和工具调用结果，并手写 ReAct 循环、计划解析、DAG 调度、上下文压缩和重试逻辑。这样我能清楚知道每轮给模型传了什么、工具结果如何回填、什么时候退出、出现超时或死循环时怎么处理。

这并不代表框架没有价值。生产环境中，如果团队已经使用 Spring AI，并且它对模型切换、可观测性和向量数据库适配足够成熟，我会优先复用。但对于底层运行时项目，自己实现关键抽象能减少框架约束，也能让我对 Function Calling、流式响应和上下文管理有更扎实的理解。

### 4. 你认为简历中最能体现技术深度的一项工作是什么？

**参考答案：**

我认为是 Sidekick 中“可持续执行的 Agent 闭环”。难点不是调用一次 LLM，而是把 Prompt、历史消息、工具定义、工具结果、Token 预算、取消信号、安全审批和渲染状态组合在一起。每轮模型可能返回多个工具调用，系统要并行执行、保持结果与 `tool_call_id` 对应，再作为 tool message 回填；如果上下文接近窗口上限，还要压缩早期历史但保留工具协议完整性。

这项工作体现了我对状态机、并发、协议适配和异常处理的综合理解。它也有明确的改进空间，例如加入更细粒度的 Trace、可配置调度策略和基于评测集的任务成功率度量。

## 二、Sidekick 项目深挖

### 5. 请画出 Sidekick 的整体架构，并说明一次请求如何流转。

**参考答案：**

可以分成六层：交互层、执行编排层、模型适配层、上下文层、工具层和安全恢复层。

1. CLI 或 TUI 接收用户输入，并处理 `/plan`、`/team`、`/model` 等命令。
2. 执行编排层根据模式进入 ReAct、Plan-and-Execute 或 Multi-Agent。
3. PromptAssembler 将基础规则、模式 Prompt、审批策略、项目记忆、长期记忆、MCP resource 索引和 Skill 索引组装成 system prompt。
4. 统一的 `LlmClient` 调用具体模型，流式接收 reasoning、正文和 tool calls。
5. `ToolRegistry` 执行文件、命令、搜索、RAG、Web、浏览器、Memory、Skill、快照或 MCP 工具，把结果回填到消息历史。
6. HITL、路径检查、命令检查、审计、取消和 SideGit 快照负责约束副作用与恢复状态。

在 ReAct 模式下，上述模型调用与工具执行会循环，直到模型不再返回工具调用，或触发 Token、轮数、停滞、取消等退出条件。

### 6. ReAct 模式是如何实现的？退出条件有哪些？

**参考答案：**

ReAct 的核心是一个显式循环。开始时把用户输入写入短期记忆，根据当前问题检索相关记忆，更新 system prompt，并把用户消息加入对话历史。每轮调用前注入 LSP 诊断、检查是否需要压缩历史、检查预算，并加载本轮待注入的 Skill 内容。

随后调用 `llmClient.chat(history, toolDefinitions, listener)`。如果返回 tool calls，就把包含 tool calls 的 assistant message 加入历史，执行工具，再把每个结果按原 `tool_call_id` 写成 tool message，进入下一轮。如果没有工具调用，就把正文作为最终答案返回。

正常退出由模型“不再调用工具”决定；防御性退出包括用户取消、Token 预算耗尽、硬轮数上限、重复工具调用导致的停滞检测，以及模型或工具调用异常。这样的设计既保留模型自主性，又防止无限循环和资源失控。

### 7. 为什么还需要 Plan-and-Execute？它和 ReAct 的适用场景有什么区别？

**参考答案：**

ReAct 适合目标明确、步骤较少、需要边观察边决策的任务，例如查找一个类并修复一个局部 Bug。优点是响应快、上下文连续；缺点是复杂任务容易出现局部最优、忘记总体目标或反复试错。

Plan-and-Execute 先让 Planner 输出结构化任务计划，每个 Task 包含 ID、描述、依赖和状态，然后按依赖关系执行。它更适合跨多个模块、需要先分析再修改和验证的任务。独立任务可以组成同一批次并行执行，失败后可以带失败原因重新规划。

代价是多一次或多次模型调用，延迟和 Token 成本更高，而且计划本身可能错误。因此项目里加入计划审核入口，让用户可以执行、取消或附加反馈后重新生成计划。实际选择上，简单任务默认 ReAct，复杂、多文件、有明显阶段依赖的任务使用 Plan-and-Execute。

### 8. 你是如何把计划建模成 DAG 并调度的？如何发现死锁或非法依赖？

**参考答案：**

每个任务包含唯一 ID、依赖 ID 列表和执行状态。每轮从所有 PENDING 任务中筛选依赖均为 COMPLETED 的任务，得到当前可执行批次；没有依赖关系的任务可以并行，有依赖的任务自然会等待前置任务完成。

调度时最多创建 4 个工作线程，避免任务数量过多导致线程和模型请求失控。每个并行任务使用独立消息上下文和输出缓冲，完成后再按任务顺序汇总，从而兼顾并发效率和终端输出可读性。

如果仍存在 PENDING 任务但找不到任何可执行任务，说明可能存在循环依赖、引用了不存在的依赖，或者前置任务失败。更完整的实现应在计划解析阶段验证 ID 唯一性、依赖存在性，并用拓扑排序检测环；执行阶段则把因前置失败无法运行的任务标记为 SKIPPED，而不是无限等待。

### 9. Multi-Agent 模式的角色如何划分？为什么不是让多个 Agent 自由聊天？

**参考答案：**

当前实现是一个受控的主从架构：Planner 负责把目标拆成 JSON 步骤；两个 Worker 按依赖批次执行；Reviewer 对单步结果进行检查；Orchestrator 维护步骤状态、分配 Worker、控制重试并汇总结果。

没有采用多个 Agent 自由对话，是因为自由对话难以保证终止、成本和责任边界，也容易产生重复工作。结构化消息和明确角色使系统更像可观测的工作流：规划者不直接修改文件，Worker 负责执行，Reviewer 负责质量门禁，Orchestrator 掌握全局状态。

当前各角色共享同一个底层 `LlmClient`，区别主要来自角色 Prompt。未来可以做模型路由，例如 Planner 使用推理能力更强的模型，Worker 使用性价比较高的模型，Reviewer 使用独立模型降低同源偏差。

### 10. Multi-Agent 中 Reviewer 判断失败后如何处理？为什么限制重试次数？

**参考答案：**

Worker 完成一步后，Reviewer 根据任务描述、依赖结果和 Worker 输出判断是否通过。若不通过，Orchestrator 将审查意见加入下一次执行上下文，让 Worker 有针对性地修正。当前每步设置有限重试，避免 Reviewer 与 Worker 因标准不一致进入无限循环。

重试次数不是越多越好。Agent 失败可能来自计划错误、工具权限不足、外部服务故障或上下文缺失，机械重试只会增加成本。更合理的策略是区分可重试错误和不可重试错误：网络超时可指数退避；参数错误应修正后重试；权限拒绝应请求用户处理；计划不合理则回到 Planner 重规划。

### 11. 多个工具调用为什么可以并行？如何保证结果不串？

**参考答案：**

模型一次响应可能返回多个 tool calls，例如同时读取多个互不依赖的文件。系统先把每个调用转换成包含 `id、name、argumentsJson` 的不可变调用对象，再交给统一批量入口执行，最大并发数为 4。

并行完成后，结果仍保留原调用 ID。回填消息历史时，每个 tool message 使用对应的 `tool_call_id`，模型因此能把结果与调用正确关联。即使完成顺序不同，也不会依赖线程返回顺序猜测对应关系。

不过并不是所有工具都适合并行。多个读操作通常安全；对同一文件的写操作、存在先后依赖的命令或共享浏览器会话可能发生竞争。生产化改进可以给工具增加只读/写入、资源键和幂等性元数据，由调度器对冲突资源串行化。

### 12. `LlmClient` 抽象解决了什么问题？如何接入一个新模型？

**参考答案：**

`LlmClient` 统一了消息、文本与图片内容、工具定义、工具调用、Token 用量和流式回调。上层 Agent 只依赖这个接口，不关心底层是 GLM、DeepSeek、Step、Kimi 还是其他 OpenAI-compatible 服务。

接入新模型时，我会先确认它的消息格式、工具调用协议、流式 SSE 格式、reasoning 字段、图片输入方式和上下文窗口。若兼容 OpenAI 协议，可继承公共客户端，配置 base URL、鉴权、模型名并覆盖少量差异；若不兼容，则独立实现 `chat`。然后在 Factory 和配置层注册 provider，并补充流式分片合并、工具参数、多模态和错误响应测试。

需要特别注意“协议看似兼容但细节不同”，例如有的模型不支持 tools，有的把推理内容放在 `reasoning_content`，有的流式 tool arguments 会被拆成很多片段。能力应该通过接口方法显式声明，而不是由上层猜测。

### 13. 流式响应如何实现？SSE 分片为什么不能直接逐行显示？

**参考答案：**

客户端发送 `stream=true` 请求，逐条读取 SSE 的 data 事件，分别提取 reasoning delta、content delta 和 tool call delta。reasoning 和正文可以通过监听器增量渲染；tool call 则必须按 index 或 ID 聚合，因为一次函数名和 JSON 参数通常会跨多个 chunk 返回。

不能把每个 SSE 行直接当成完整消息。网络分片不等于语义分片，JSON 参数可能从任意字符处分割，甚至多个工具调用交错出现。正确做法是维护累加器，直到服务端结束标记后再构造完整 `ToolCall`。还要处理心跳、空行、`[DONE]`、非 2xx 响应、超时和用户取消。

终端渲染也要区分 reasoning、正文和工具阶段，执行工具前刷新 Markdown 缓冲，避免未换行文本与审批提示错位。

### 14. Prompt 为什么要分层，而不是写成一个很长的字符串？

**参考答案：**

分层主要解决可维护性、复用和组合问题。Sidekick 将基础行为、人格、执行模式、审批策略、运行时日期、项目上下文、Memory、Skills、上下文管理和交接规则分别维护，再由 `PromptAssembler` 按当前模式组装。

这样 ReAct、Planner、Plan Task、Team Planner、Worker、Reviewer 可以共享基础规则，同时保留角色差异；审批模式切换也不需要复制整份 Prompt。动态内容和静态内容分开后，更容易控制 Token，也有利于利用模型的 Prompt Cache。

风险是不同层之间可能规则冲突。因此需要固定优先级、对关键章节做校验，并为不同 `PromptMode` 编写快照或单元测试。Prompt 变更也应像代码一样评审和回归，而不是只靠人工体验。

### 15. Sidekick 的三层记忆分别是什么？为什么不能只保存完整对话？

**参考答案：**

第一层是短期对话记忆，保存近期用户、助手和工具交互，用于保持当前任务连续性。第二层是长期记忆，只保存用户明确要求记住的稳定事实，并区分项目级和全局级作用域。第三层是外部检索，包括代码 RAG、MCP resource 和按需加载的 Skill，它们不是普通聊天历史，而是根据当前任务动态获取的知识。

不能无限保存完整对话，因为模型上下文窗口有限，工具结果和图片尤其占 Token。历史过长会提高成本、延迟，并让关键信息被噪声淹没。项目同时使用预算裁剪和 LLM 摘要压缩：保留近期原始消息，把早期内容压缩为结构化摘要，并尽量保留目标、已完成工作、关键文件、工具协议和未决问题。

长期记忆也不能自动把所有对话持久化，否则会保存错误、临时任务和隐私信息，所以只有明确保存意图时才写入。

### 16. 长期记忆的检索如何排序？时间衰减有什么意义？

**参考答案：**

检索需要同时考虑文本相关性、来源、作用域和时间。当前思路是先从短期和长期记忆中找候选项，再计算匹配分数；短期上下文通常权重更高，长期事实结合查询相关性和时间衰减排序，并优先选择当前项目作用域，同时允许检索全局偏好。

时间衰减用于降低旧的临时信息影响，但不能简单地认为越旧越不重要。例如“项目使用 Java 17”可能长期有效，而“今天正在修改某个文件”很快失效。因此更好的设计是给记忆增加类型、有效期、置信度和最后验证时间，对稳定偏好弱衰减，对运行状态强衰减，并允许新事实覆盖或使旧事实失效。

### 17. 上下文压缩时，怎样避免破坏 Function Calling 协议？

**参考答案：**

工具调用通常由一条带 tool calls 的 assistant message 和若干对应的 tool message 组成。如果只删其中一半，下一次请求可能违反模型 API 的消息约束，也会让模型不知道工具结果对应哪个调用。

所以压缩时应把一次工具交互视为原子组：要么完整保留，要么把其业务结论写入摘要并整体移除。近期未完成的调用、错误信息和产生副作用的工具结果应优先保留。摘要至少包含当前目标、已完成步骤、关键观察、修改过的文件、失败原因和下一步计划。

此外，应在压缩后做协议校验，例如 assistant tool call 后存在相应 tool response、ID 可匹配、首条仍是 system message。压缩不是简单截断字符串，而是对结构化会话状态做变换。

### 18. Sidekick 的代码 RAG 是怎么做的？为什么 Java 文件要按 AST 切分？

**参考答案：**

索引流程包括遍历项目文件、过滤构建目录、按类型切片、生成 Embedding、保存向量和代码关系。Java 文件使用 JavaParser 解析 AST，可以按类、接口、方法等语义边界切分；普通文本或无法解析的文件再按长度分块。

AST 切分优于固定字符切分，因为一个方法通常是完整的行为单元，类名、方法签名和上下文可以一起保存。固定切分可能把方法从中间截断，让召回结果缺少定义或关键分支。系统还可以保存调用、继承等关系，在召回一个方法后扩展相关符号。

查询时生成查询向量，在 SQLite 中做轻量向量相似度搜索，并融合关键词命中、类型权重和同文件结果限制，最后格式化为带路径和代码范围的上下文。精确定位仍应优先使用文件名、符号和文本搜索，RAG 主要用于语义探索。

### 19. 为什么选择 SQLite 做 Sidekick 的向量存储？它有什么局限？

**参考答案：**

Sidekick 是本地 CLI，SQLite 的优点是零部署、单文件持久化、事务简单、便于随项目携带，适合中小代码库。它可以同时存代码块元数据、向量和关系，不需要用户安装 Elasticsearch 或独立向量数据库。

局限是大规模向量检索性能有限，如果直接在 Java 中遍历所有向量计算相似度，复杂度接近 O(n)。并发写入能力也比服务型数据库弱。优化方向包括增量索引、文件哈希去重、批量事务、内存缓存、使用支持向量扩展的 SQLite，或者在超大仓库中切换 HNSW、Qdrant、Milvus 等后端。

这个选择体现的是场景适配：本地开发工具优先降低部署成本，企业知识库则更适合 Elasticsearch 等可横向扩展的系统。

### 20. MCP 是什么？Sidekick 为什么同时支持 stdio 和 Streamable HTTP？

**参考答案：**

MCP 可以理解为模型应用与外部工具、资源之间的标准协议，底层使用 JSON-RPC 2.0。客户端通常先初始化并协商能力，再列出 tools/resources，调用工具，并处理响应、错误和通知。

stdio 适合本地 MCP Server。Sidekick 启动子进程，通过标准输入发送 JSON-RPC，通过标准输出读取响应，部署简单且无需开放端口。Streamable HTTP 适合远程或常驻服务，便于跨进程和跨主机复用，也更适合鉴权和集中维护。

实现上要解决请求 ID 与异步响应匹配、并发 pending request、进程退出、stderr 与 stdout 分离、HTTP session、超时和资源清理。Server 返回的工具会被动态注册到统一 `ToolRegistry`，但仍要经过审计和审批，不能因为是 MCP 工具就绕过安全策略。

### 21. 普通 HTTP 抓取失败时，为什么要切到 Chrome DevTools Protocol？

**参考答案：**

普通 HTTP 抓取适合 SSR 页面，速度快、资源占用低。但 SPA 的正文由 JavaScript 渲染，反爬站点可能要求 Cookie、浏览器指纹或动态参数，登录页面还需要复用用户会话，普通请求可能只得到空壳 HTML、验证码或登录页。

因此系统先使用 `web_fetch`，若检测到正文为空、SPA/反爬特征或登录要求，再通过 MCP 接入 Chrome DevTools，获取渲染后的 DOM。对于需要登录态的页面，复用用户主动连接的浏览器会话；公开页面不应一开始就切浏览器，以免提高延迟和隐私风险。

这里还需要 SSRF 防护、URL 协议和内网地址限制、敏感页面策略，以及明确区分 Agent 自己打开的标签页与用户原有页面。

### 22. Skill 系统解决了什么问题？为什么只在启动时注入索引？

**参考答案：**

工具定义告诉模型“能做什么”，Skill 则告诉模型“在特定场景下应该怎么做”。一个 Skill 包含名称、描述、完整操作手册，以及可选参考资料或脚本。

如果启动时把所有 Skill 全文放进 system prompt，会大量消耗 Token，并让无关规则干扰当前任务。因此只注入名称和描述组成的轻量索引；当模型判断某个 Skill 与任务匹配时，调用 `load_skill`，系统再把正文放入缓冲，在下一轮请求中注入。

项目支持内置、用户和项目三级来源，后者可覆盖前者。实现时要处理名称冲突、启停状态、正文大小限制、一致性注入和缓存淘汰。LRU 只能控制内存占用，是否把 Skill 带入下一轮仍应根据任务相关性和 Token 预算决定。

### 23. Sidekick 如何控制命令和文件操作的安全风险？

**参考答案：**

安全模型不是容器级沙箱，而是多层防护。第一层是路径校验，限制文件操作在项目范围内并防止路径穿越。第二层是命令快速拒绝，对明显危险命令进行检查。第三层是 HITL 审批，写文件、执行命令、创建项目、回滚以及 MCP 副作用工具在策略要求时需要用户确认。第四层是审计日志，记录工具和参数。第五层是操作前后快照，出现问题可以回滚。

我会明确告诉用户这不是强隔离：本地进程仍继承当前用户权限，不能抵御所有恶意命令。生产级强隔离需要容器、gVisor 或 microVM，并配合网络、文件系统和凭证最小权限。项目当前更适合可信用户的本地开发场景。

### 24. 快照回滚是如何设计的？为什么不直接依赖项目自己的 Git？

**参考答案：**

快照服务在一次 Agent turn 前记录状态，执行后异步生成后置快照。回滚时可以恢复到某个 turn 的前置状态。它使用独立的 SideGit 状态管理，目标是即使用户仓库没有初始化 Git、存在未提交修改，或者用户不希望 Agent 操作业务分支，也能提供恢复能力。

不能简单执行 `git reset --hard`，因为它可能删除用户原有未提交工作。安全回滚需要区分 Agent 产生的变化和用户已有变化，并在恢复前检查目标。并发写入时还要保证快照时序和文件一致性。

对于二进制文件、大文件和未跟踪文件，快照成本也需要控制。可以使用忽略规则、增量对象和大小上限，并在无法完整恢复时明确提示边界。

### 25. 如何避免 Agent 陷入死循环或重复调用同一个工具？

**参考答案：**

首先设置硬轮数和总 Token 预算，保证任何任务都有资源上限。其次记录最近工具调用的名称和规范化参数，若相同调用连续出现且结果没有变化，就判定停滞。还可以记录错误指纹，避免模型在相同输入下重复执行失败命令。

单纯比较工具名不够，因为同一个读取工具访问不同文件是正常的；也不能只比较原始 JSON 字符串，因为字段顺序不同但语义可能相同。因此应规范化参数，并结合结果摘要和状态变化判断是否取得进展。

触发停滞后，可把原因反馈给模型要求换策略；多次仍无进展则退出并向用户说明已经尝试的步骤和阻塞点，而不是无限消耗 Token。

### 26. 模型切换后，历史上下文和 Token 预算如何处理？

**参考答案：**

切换模型不仅是替换 API Key。不同模型的上下文窗口、工具能力、图片能力、Prompt Cache 和 Token 计算方式可能不同。项目通过 `ContextProfile.from(llmClient)` 更新上下文窗口、短期记忆预算和压缩阈值，同时更新 ToolRegistry 中的当前 provider/model 信息。

已有历史如果超过新模型窗口，需要在下一次调用前压缩；如果新模型不支持工具，Prompt 中必须移除工具规则，并且不能让它伪造工具调用。多模态历史也应根据新模型能力剥离或转换。

更完善的实现会在切换时先做能力检查，展示可能丢失的能力，并对历史进行一次预估和兼容性迁移。

### 27. 这个项目如何支持取消？为什么仅仅中断 UI 不够？

**参考答案：**

取消需要从输入层传播到模型调用、Agent 循环、工具执行和并行任务。项目通过取消上下文或 Token 在关键边界检查：调用模型前后、进入下一轮前、Multi-Agent 批次之间都能尽快退出。

只让 UI 停止显示是不够的，因为后台线程、HTTP 请求或子进程可能仍在运行并产生副作用。理想实现应取消 OkHttp Call、关闭流式响应、终止可终止的子进程、取消 Future，并确保 finally 中释放线程池和资源。

对于已经开始的不可逆外部操作，取消只能阻止后续步骤，不能假装回滚成功，因此需要在结果中说明已完成和未完成的操作。

### 28. 如果让你继续改进 Sidekick，你会优先做哪三件事？

**参考答案：**

第一，建立可量化评测体系。准备代码定位、Bug 修复、多文件重构、Web 检索等任务集，记录成功率、工具调用次数、Token、延迟和人工接管率，避免只凭主观体验调整 Prompt。

第二，加强调度与安全。为工具增加副作用级别、资源锁、幂等性和可重试元数据；把本地执行逐步迁移到可选容器或 microVM，并限制网络和凭证访问。

第三，完善可观测性。为每个 run、LLM call、tool call 和 Agent step 建立 Trace ID，输出结构化日志和耗时分布，支持回放。这样才能定位问题究竟来自模型、Prompt、检索、工具还是调度器。

## 三、IntelliDoc 企业知识库项目深挖

### 29. 请介绍 IntelliDoc 的端到端架构。

**参考答案：**

用户通过 Spring Boot API 上传文档。小文件可以直接上传，大文件走分片上传；服务端用 Redis Bitmap 记录分片到达状态，用 MinIO 保存对象，并通过 MD5 做秒传、断点续传和最终合并校验。元数据保存到关系数据库。

上传完成后发送 Kafka 消息，把解析、切片、向量化和索引从请求线程解耦。消费者用 Apache Tika 提取文本，按文档结构和长度切片，调用 Embedding 模型生成 2048 维向量，并写入 Elasticsearch。查询时先做租户与权限过滤，再分别进行 KNN 向量召回和 BM25 关键词召回，融合或重排后把相关片段交给大模型生成答案。

问答链路通过 WebFlux 接收模型 SSE 流，并用 WebSocket 实时推送给前端。会话历史存 Redis；向量服务失败时降级为关键词检索，保证基本可用。

### 30. 为什么文档处理要用 Kafka 异步化？直接同步处理有什么问题？

**参考答案：**

文档解析、切片、Embedding 和索引耗时长，而且耗时随文件大小和模型服务状态波动。同步处理会长期占用 HTTP 线程，容易超时，也无法平滑吸收上传高峰。

Kafka 将上传接口与处理 Worker 解耦：接口完成对象存储和元数据落库后快速返回任务 ID，后台消费者按能力处理；通过增加分区和消费者可以扩容。Kafka 还保留消息，短暂故障后可继续消费。

但异步化引入了最终一致性和重复消费。数据库中要记录任务状态与版本，消费者必须幂等；失败要区分重试和死信，前端通过轮询、SSE 或 WebSocket查看状态。发送消息与数据库提交之间还存在一致性问题，生产环境可用 Outbox Pattern 解决。

### 31. Kafka 消费者如何实现幂等？如果消息处理到一半宕机会怎样？

**参考答案：**

我会使用业务幂等键，例如 `documentId + documentVersion + stage`。消费者处理前查询任务状态或尝试插入唯一记录，已成功的阶段直接返回。索引文档使用稳定 ID，例如 `documentId_chunkIndex_version`，重复写入会覆盖而不是新增。

消费顺序应是先完成业务写入，再提交 offset。若业务写完但 offset 未提交就宕机，消息会重复投递，但幂等设计保证结果不重复。如果在处理中宕机，任务保持 PROCESSING 或阶段性状态，超时扫描可以恢复。

对于多阶段流程，最好把解析、向量化、索引各自建模为状态，避免一个大事务。超过最大重试次数进入死信队列，并保存异常、重试次数和原消息，支持人工修复后重放。

### 32. 如何解决“数据库写成功但 Kafka 消息发送失败”的一致性问题？

**参考答案：**

如果先写数据库再发 Kafka，发送失败会导致文档永远不处理；如果先发消息再写数据库，消费者可能找不到文档记录。仅靠 try-catch 和重试仍有进程宕机窗口。

我会使用本地事务 Outbox：在同一个数据库事务中写文档元数据和 outbox 事件。后台发布器轮询或通过 CDC 把未发布事件发到 Kafka，成功后标记已发布。由于 Kafka 可能重复投递，消费者仍需幂等。

这样把跨系统的强一致问题转化为“数据库事务 + 最终一致重试”。如果业务允许，也可以用定时补偿扫描未处理文档作为兜底，但 Outbox 的状态更清晰、可审计。

### 33. 大文件分片上传的具体流程是什么？Redis Bitmap 如何使用？

**参考答案：**

客户端先调用初始化接口，携带文件名、大小、文件 MD5 和分片数量。服务端检查完整文件是否已存在；若存在可直接秒传，否则返回 uploadId 和已上传分片列表。客户端并发上传各分片，服务端保存到临时对象路径，并对 `upload:{id}:chunks` 的对应 bit 置 1。

合并前检查 Bitmap 中已到达分片数是否等于总数，并验证分片编号和大小。随后按顺序流式合并到 MinIO，避免把整个文件加载进 JVM 堆，计算最终 MD5 与客户端值比对。成功后原子更新文件状态并清理临时分片和 Redis key。

Bitmap 内存效率高，适合判断大量分片是否到齐，但 Redis 不是唯一事实来源。对象存储和数据库状态也要能用于恢复，避免 Redis 数据丢失后无法继续上传。

### 34. MD5 秒传会不会有安全和正确性问题？

**参考答案：**

MD5 可用于工程上的内容去重和完整性快速校验，但它已不适合安全签名，存在碰撞风险。不能只凭客户端传来的 MD5 就把另一个租户的文件直接关联给当前用户，否则会产生越权和信息泄露。

服务端应在受信任边界内重新计算摘要，并把去重和授权分开：物理对象可以按内容哈希复用，但每个租户仍要创建独立逻辑文件记录和权限关系。对安全敏感场景可使用 SHA-256。秒传接口也不应返回“某个敏感文件是否存在”等可探测信息。

### 35. Apache Tika 在文档解析中的作用是什么？如何处理解析失败或超大文档？

**参考答案：**

Tika 统一抽象 PDF、Word、PPT、TXT 等格式，识别 MIME 类型并提取正文和元数据，避免每种格式写一套解析代码。

实际使用时要限制文件大小、解析时间、嵌套深度和输出字符数，因为压缩炸弹、损坏文件或复杂 PDF 可能耗尽 CPU 和内存。解析最好运行在隔离 Worker 中，并设置超时。扫描版 PDF 没有文本时需要进入 OCR 分支；加密文档应标记为需要密码或不可解析，而不是生成空索引。

处理结果要保留页码、标题层级、段落和表格等来源信息，这些元数据会影响切片质量，也便于答案引用原文位置。

### 36. 文档应该如何切片？固定长度切片有什么缺点？

**参考答案：**

切片目标是在语义完整性和召回粒度之间平衡。块太大，Embedding 混入多个主题且占用上下文；块太小，信息不完整。固定长度切分实现简单，但可能把标题与正文、问题与答案、表格行或一个完整定义拆开。

更好的策略是先按标题、段落、列表、页码等结构切分，再对超长段落按 Token 长度二次切分，并保留适量 overlap。每个 chunk 记录文档 ID、租户、权限标签、页码、章节路径、顺序和版本。

切片参数不能只凭经验，应建立问答测试集，比较 Recall@K、MRR、答案正确率和上下文长度，再选择不同文档类型的策略。

### 37. Elasticsearch 中 2048 维向量如何存储和检索？

**参考答案：**

为每个 chunk 建立文档，正文使用 text 字段和 IK 分词，Embedding 使用 `dense_vector`，维度必须与模型输出一致，例如 2048，并配置余弦或点积相似度及 KNN 索引。租户、组织、文档 ID、权限标签、版本等使用 keyword 字段。

查询时把问题转为同模型向量，执行 KNN 召回，并在过滤条件中限制租户和权限。`k` 是最终候选数，`num_candidates` 是近似搜索阶段候选池，后者越大召回可能越好但延迟越高。

向量维度较高会增加内存和磁盘开销，需要通过真实数据评估分片数、副本数、HNSW 参数和量化方案。Embedding 模型升级时向量空间发生变化，必须做版本化索引和灰度重建，不能混用新旧向量。

### 38. KNN 与 BM25 的两阶段混合检索如何实现？为什么需要二者结合？

**参考答案：**

向量检索擅长语义相近表达，例如“员工离职流程”和“解除劳动关系步骤”；BM25 擅长精确关键词、型号、编号、人名和错误码。只用向量可能错过精确实体，只用 BM25 又难以处理同义改写。

实现上可以并行召回两组候选，分别取 top K，再用 Reciprocal Rank Fusion 合并排名；也可以先 KNN 扩大语义候选，再用 BM25 或 Cross-Encoder 对候选重排。由于两种分数尺度不同，不宜未经归一化直接相加。

权限过滤必须在召回阶段就应用，不能先召回所有租户数据再在应用层删除，否则会浪费候选位，还可能通过分数或日志泄露信息。

### 39. 为什么使用 IK 分词器？中文检索有哪些特殊问题？

**参考答案：**

中文文本没有天然空格，标准分词器通常不能得到理想词项。IK 提供细粒度和智能分词模式，适合中文 BM25 检索，并可以维护业务词典。

问题包括新词、人名、产品型号和中英文混合内容。过细分词会降低精确度，过粗又影响召回。索引 analyzer 和查询 analyzer 可以采用不同策略，并结合同义词、拼音、keyword 子字段和领域词典。

修改分词或同义词规则可能需要重建索引，因此要使用索引别名和版本化迁移。效果同样应该用查询集评估，而不是只看几个示例。

### 40. 基于组织标签的 RBAC 如何建模？它和普通角色权限有什么区别？

**参考答案：**

基础 RBAC 包括用户、角色、权限以及用户角色关系。但企业文档权限不仅取决于角色，还取决于组织、文档归属、密级、标签和创建者，因此更接近 RBAC 与 ABAC 的结合。

认证后，JWT 中保存用户 ID、租户 ID和必要的粗粒度声明；服务端从可信数据源加载角色和组织范围，生成可访问条件。接口层通过 Spring Security 做功能权限检查，查询 Elasticsearch 时再加入租户、组织路径、文档标签等过滤，下载 MinIO 对象时也必须再次授权。

不能只依赖前端隐藏按钮，也不应把巨大权限列表长期塞进 JWT，因为权限变更后旧 Token 仍有效。可以使用短期 access token、权限版本号或服务端缓存，并在敏感操作时实时校验。

### 41. 为什么同时使用 WebFlux、SSE 和 WebSocket？会不会过度设计？

**参考答案：**

模型供应商通常通过 SSE 返回单向流。WebFlux 适合以非阻塞方式消费上游流并处理背压，避免为每个长连接占用一个阻塞线程。向浏览器返回答案时，如果只需要服务器向客户端推送，直接透传 SSE 往往最简单；WebSocket 适合双向控制，例如取消生成、会话事件和状态通知。

如果项目只是单次问答，SSE 足够，额外引入 WebSocket 确实可能增加复杂度。我的设计选择应由实际交互需求决定，而不是为了堆技术栈。无论哪种方式，都要处理断线重连、心跳、取消、消息顺序、网关超时和慢客户端背压。

还要避免在 WebFlux 链路中执行阻塞的数据库、Tika 或传统 HTTP 调用；确实需要阻塞操作时应切换专用调度器或改用响应式客户端。

### 42. Redis 如何保存多轮对话？为什么只保留 7 天？

**参考答案：**

可以按 `tenant:user:session` 保存会话元数据，并用 List、ZSet 或序列化对象保存消息。消息需要角色、内容、时间、引用文档和 Token 等字段，按时间读取最近窗口。每次写入刷新或设置 7 天 TTL，使临时会话自动清理，避免 Redis 无限增长。

模型请求不能无脑带上全部历史，应按 Token 预算保留最近消息，并对较早对话摘要。重要业务记录如果要求长期审计，不应只放 Redis，而应异步落数据库或对象存储，并遵循数据保留和隐私政策。

缓存穿透、热会话、大 value 和并发更新也要考虑。可使用 Lua 或事务保证追加消息与更新 TTL 的原子性。

### 43. 向量 API 失败时降级到文本检索，如何避免把故障放大？

**参考答案：**

调用 Embedding API 时设置较短超时、有限重试和指数退避，并通过熔断器统计失败率。熔断打开后直接跳过向量调用，使用 BM25 文本检索，而不是每个请求都等待模型超时。恢复阶段允许少量探测请求半开验证。

降级结果应在内部指标中标记，必要时向用户提示“当前使用关键词检索”，便于解释效果变化。对同一查询可以缓存 Embedding，但要把模型版本纳入 key。

还需区分限流、网络超时、请求参数错误和服务端错误：参数错误重试没有意义；429 应尊重 Retry-After；持续故障应触发告警。降级保证的是可用性，不代表结果质量完全等价。

## 四、Java 基础与并发

### 44. HashMap 在 Java 8 中的数据结构是什么？什么时候树化？

**参考答案：**

HashMap 使用数组加链表加红黑树。key 的 hash 经扰动后定位桶；发生冲突时先形成链表。当单个桶节点数达到 8 且数组容量至少为 64 时尝试树化，否则优先扩容。树节点减少严重哈希冲突时的查询复杂度。

默认负载因子 0.75，在元素数超过 `capacity × loadFactor` 时扩容，通常容量翻倍。HashMap 允许一个 null key，不保证顺序，也不是线程安全的。并发写应使用 ConcurrentHashMap，而不是仅通过外部偶然无冲突来假设安全。

### 45. ConcurrentHashMap 为什么比给整个 HashMap 加 synchronized 更适合并发？

**参考答案：**

Java 8 的 ConcurrentHashMap 不再使用旧版 Segment 作为主要结构，而是数组、链表/红黑树，配合 CAS 和桶级 synchronized。初始化、空桶插入等场景可用 CAS，发生冲突时只锁对应桶，读取大多不加锁，因此并发度高于给整个 Map 加一把全局锁。

它不允许 null key/value，因为并发环境中 `get` 返回 null 无法区分“没有映射”和“值就是 null”。复合操作不能写成 `containsKey` 后 `put`，应使用 `putIfAbsent`、`compute` 等原子方法。

在 Sidekick 中，工具注册表、步骤重试计数等共享状态适合使用并发容器，但容器线程安全不代表多个业务操作整体原子，仍要分析状态转换。

### 46. volatile 能保证什么？为什么不能保证 `count++` 安全？

**参考答案：**

volatile 保证变量写入对其他线程可见，并限制特定指令重排序，建立写与后续读之间的 happens-before 关系。它适合取消标志、配置引用或状态发布。

`count++` 包含读取、加一、写回三个步骤，两个线程可能读到同一旧值，因此即使 count 是 volatile 也会丢失更新。计数应使用 AtomicInteger/LongAdder，或在同一锁中执行。

Sidekick 的取消状态可以用 volatile 或原子变量；而步骤从 PENDING 到 RUNNING 的条件更新，需要 CAS、锁或集中调度保证只能被一个 Worker领取。

### 47. synchronized 和 ReentrantLock 有什么区别？如何选择？

**参考答案：**

synchronized 是 JVM 内置监视器，语法简单，退出代码块会自动释放锁，适合大多数互斥场景。ReentrantLock 提供 `tryLock`、可中断获取、超时、公平锁和多个 Condition，控制更灵活，但必须在 finally 中 unlock。

两者都可重入并提供内存可见性。选择时优先可读性；如果需要超时、取消、多个等待条件或避免无限阻塞，再用 ReentrantLock。不能仅凭“Lock 性能更高”做选择，现代 JVM 已对 synchronized 做了大量优化。

### 48. ThreadLocal 为什么可能导致内存泄漏？如何避免？

**参考答案：**

ThreadLocalMap 的 key 是 ThreadLocal 的弱引用，value 是强引用。当 ThreadLocal 对象被回收后，key 变 null，但在线程长期存活时 value 可能继续被线程引用。在线程池中线程不会很快销毁，因此大对象或用户上下文可能长期滞留，还可能污染下一次任务。

使用原则是在 try/finally 中 `remove()`，不要把生命周期短的数据永久绑定到线程池线程。异步和响应式编程中，请求可能跨线程，普通 ThreadLocal 也无法可靠传播，应使用显式上下文或框架提供的 Context。

### 49. Sidekick 的并行工具执行使用固定线程池，有哪些潜在问题？

**参考答案：**

固定并发上限可以控制资源，但如果每个批次都新建线程池，会产生线程创建和销毁开销；如果任务阻塞且超时取消无效，线程仍可能被占用。多个 Agent 批次同时运行时，还可能突破系统级总并发限制。

改进方式是使用生命周期统一的有界 Executor，设置队列、线程命名、拒绝策略和指标；把模型调用、文件 IO、命令执行等不同资源放入不同隔离池。Future 超时后要调用 cancel，并让具体工具响应中断。共享文件或浏览器资源还需资源级串行化。

Java 21 可以考虑虚拟线程处理大量阻塞 IO，但本项目基于 Java 17，因此仍需谨慎管理平台线程。

### 50. ArrayList 和 CopyOnWriteArrayList 的适用场景分别是什么？

**参考答案：**

ArrayList 适合单线程或外部同步场景，随机访问快，尾部追加摊销 O(1)，但并发读写不安全。CopyOnWriteArrayList 每次写操作复制底层数组，读操作无需加锁，迭代器看到创建时快照。

因此 CopyOnWriteArrayList 适合读多写极少、集合规模不大，例如监听器或配置快照；不适合高频追加的聊天消息或工具结果，否则复制成本和内存抖动很大。Agent 的单次历史通常由一个控制线程维护，可使用 ArrayList；真正跨线程共享时应设计归属关系，而不是盲目换并发集合。

### 51. Java 异常体系中 checked exception 和 unchecked exception 如何使用？

**参考答案：**

checked exception 适合调用方能够合理恢复或必须显式处理的情况，例如 IO；unchecked exception 通常表示编程错误、非法状态或跨层统一业务异常。不能机械地把所有异常 catch 后返回空值，否则会隐藏故障。

在 Agent 项目中，模型网络错误应保留原因并转换为对用户可理解的错误；工具执行错误可作为工具结果回填，让模型决定换策略；取消应单独识别，不能当普通失败重试。日志记录完整堆栈，对外输出脱敏摘要，避免 API Key、命令环境和用户文档泄露。

### 52. 反射的优缺点是什么？Spring 为什么大量使用反射？

**参考答案：**

反射允许运行时读取类、方法、字段和注解，并动态创建或调用对象。Spring 用它完成组件扫描、依赖注入、配置绑定、AOP 代理和序列化适配。

缺点是类型检查推迟到运行时、可读性较差、可能破坏封装，并存在一定性能和原生镜像兼容成本。现代 JVM 下普通业务场景的反射开销通常不是第一瓶颈，但框架会缓存元数据、生成代理或 MethodHandle 降低重复成本。

应用代码应优先接口和显式注册，只有插件、框架扩展点或通用映射等场景再使用反射。

### 53. 你如何设计一个线程安全的任务状态机？

**参考答案：**

先定义合法状态和转换，例如 PENDING→RUNNING→COMPLETED/FAILED，FAILED 可根据策略进入 RETRYING，取消可进入 CANCELLED。禁止 COMPLETED 再回到 RUNNING。

单进程中可以用 AtomicReference 的 compareAndSet 保证条件转换，或由单一调度线程独占状态修改；数据库场景可使用版本号乐观锁执行 `update ... where status=PENDING and version=?`。状态变更和事件发布若跨系统，应配合事务 Outbox。

还需要记录时间、执行者、重试次数和失败原因，保证状态可审计。并发安全不仅是字段不出错，还包括不会重复领取、不会漏发事件，以及崩溃后可以恢复。

## 五、Spring、数据库与中间件

### 54. Spring IoC 和 AOP 分别解决什么问题？

**参考答案：**

IoC 把对象创建和依赖关系交给容器管理，业务类依赖接口而不是自行 new 具体实现，便于替换、测试和统一生命周期管理。依赖注入是 IoC 的主要实现方式，构造器注入通常比字段注入更清晰，也能保证必要依赖不为空。

AOP 把事务、权限、日志、指标等横切逻辑从业务方法中抽离。Spring 常通过 JDK 动态代理或 CGLIB 代理实现。需要注意同类内部方法调用绕过代理、非 public 方法和异常被吞掉可能导致事务不生效。

### 55. Spring Boot 自动配置的基本原理是什么？

**参考答案：**

Spring Boot 根据 classpath、配置属性和已有 Bean 条件性导入自动配置类，常见条件包括 `@ConditionalOnClass`、`@ConditionalOnMissingBean` 和 `@ConditionalOnProperty`。自动配置提供合理默认值，用户声明自己的 Bean 时通常可以覆盖。

启动问题排查时，我会查看条件评估报告、Bean 定义来源和配置绑定结果，而不是把自动配置理解为魔法。自定义 starter 也应把配置属性、自动配置类和依赖边界分开。

### 56. MySQL 的事务隔离级别有哪些？什么是 MVCC？

**参考答案：**

标准隔离级别包括读未提交、读已提交、可重复读和串行化。隔离越强，并发能力通常越低。InnoDB 默认常见为可重复读，通过 MVCC 和必要的锁减少读写冲突。

MVCC 利用隐藏事务字段、undo log 和 Read View，让快照读读取符合可见性规则的版本。当前读如 `select ... for update` 会读取最新版本并加锁。可重复读可以避免普通快照读的不可重复读，并通过 next-key lock 在特定当前读场景处理幻读。

实际选择要结合业务。一致性要求、查询类型和锁冲突比背诵隔离级别更重要。

### 57. 联合索引的最左前缀原则是什么？哪些情况可能导致索引失效？

**参考答案：**

联合索引按列顺序组织，例如 `(tenant_id, status, created_at)`，查询从最左列开始连续使用等值条件时效果最好；遇到范围条件后，后续列通常难以继续用于定位，但仍可能用于索引下推或覆盖。

常见问题包括对索引列做函数或隐式类型转换、前导模糊匹配、选择性太低、OR 条件不合适，以及查询返回数据比例过高导致优化器选择全表扫描。是否使用索引不能凭感觉，应通过 EXPLAIN 和实际执行统计验证。

企业知识库查询常以 tenant_id 作为索引首列，避免跨租户扫描；状态和时间顺序则根据主要查询模式设计。

### 58. Redis 常见数据类型及适用场景是什么？

**参考答案：**

String 适合缓存、计数和分布式锁值；Hash 适合对象字段；List 适合简单队列或有序消息；Set 适合去重和集合运算；ZSet 适合排行榜和按时间排序；Bitmap 适合签到或分片完成状态；HyperLogLog 适合近似基数统计；Stream 适合带消费组的消息流。

IntelliDoc 中 Bitmap 用于分片状态，会话可以用 List/ZSet 或序列化对象。选型不能只看命令方便，还要评估 key 数、value 大小、TTL、持久化、热 key 和集群槽位。

### 59. Kafka 如何保证分区内有序？为什么不能保证全局有序？

**参考答案：**

Kafka 在单个 partition 内按 offset 追加，因此同一分区内有序。Producer 使用同一个业务 key，例如 documentId，可以让同一文档的事件进入同一分区。消费组中一个分区同一时刻只分配给一个消费者。

多个分区可以并行，彼此没有统一顺序，所以默认不保证全局有序。若业务强制全局有序，只能使用单分区或在业务层增加排序协调，但吞吐会下降。文档处理通常只要求同一文档或同一版本有序，不需要牺牲整个 Topic 的并行能力。

### 60. HTTP、SSE 和 WebSocket 的区别是什么？

**参考答案：**

普通 HTTP 是请求-响应模型，适合短交互。SSE 基于 HTTP 长连接，由服务端单向推送文本事件，浏览器支持自动重连，适合模型逐字输出和通知。WebSocket 握手后建立全双工连接，客户端和服务端都能主动发送，适合实时协作、控制和高频双向消息。

SSE 协议简单、经过代理更容易，但只支持文本且主要是单向；WebSocket 更灵活，但连接管理、心跳、负载均衡和鉴权续期更复杂。选择应以交互需求为准。

### 61. JVM 运行时数据区包括哪些部分？哪些是线程私有的？

**参考答案：**

线程私有区域包括程序计数器、Java 虚拟机栈和本地方法栈。程序计数器记录当前线程执行位置；虚拟机栈由栈帧组成，保存局部变量表、操作数栈、动态链接和返回地址。线程共享区域主要是堆和方法区，HotSpot 中方法区通常由 Metaspace 实现；堆存放大多数对象，Metaspace 保存类元数据。

直接内存不属于 JVM 规范定义的运行时数据区，但 NIO 和网络库会大量使用，配置不当同样可能 OOM。排查内存问题时要先看具体错误类型：`Java heap space`、`Metaspace`、`Direct buffer memory` 或无法创建本地线程分别指向不同原因，不能一律通过增大堆解决。

### 62. 你了解哪些垃圾收集器？如何排查频繁 Full GC？

**参考答案：**

Java 17 常见收集器包括 Serial、Parallel、G1，也可以选择 ZGC 或 Shenandoah 等低停顿收集器。G1 把堆划分为 Region，根据收益优先回收，兼顾吞吐与可预测停顿，适合较大的堆。

排查频繁 Full GC 时，先收集 GC 日志、堆使用曲线、对象分配速率和停顿时间，判断是内存泄漏、堆过小、大对象、元空间增长还是显式 GC。然后通过 heap dump 和 MAT 等工具查看支配树与 GC Root 引用链。

结合 Sidekick 场景，应特别关注历史消息、图片 Base64、工具大结果、Embedding 数组和线程池对象是否被长期引用。优化首先是修复生命周期和限制结果大小，而不是直接提高 `-Xmx`。

### 63. Java IO、NIO 和异步 IO 有什么区别？项目中如何选择？

**参考答案：**

传统 IO 以 Stream 为中心，调用通常阻塞，代码直观，适合普通文件操作。NIO 使用 Channel、Buffer 和 Selector，可以进行非阻塞多路复用，适合大量网络连接。NIO.2 还提供异步文件和网络 API。

大文件合并不一定需要复杂的 Selector，但应使用缓冲流或 Channel 流式复制，避免一次性读入堆。高并发网络连接可以由 Netty 或 WebFlux 等成熟框架管理。选择依据是并发规模和阻塞特征，不是 NIO 一定比 IO 快；少量本地文件读写使用简单阻塞 IO 往往更可靠。

### 64. Java 类加载过程和双亲委派模型是什么？

**参考答案：**

类的生命周期包括加载、验证、准备、解析、初始化、使用和卸载。加载阶段读取字节码并生成 Class 对象；验证保证格式与语义安全；准备为静态变量分配内存并设默认值；初始化执行静态赋值和静态代码块。

双亲委派是类加载器先委托父加载器查找，父加载器无法加载时再由自己尝试，能够避免核心类被应用重复或恶意覆盖。插件系统、SPI、应用服务器等场景可能需要线程上下文类加载器或打破部分委派。

Sidekick 如果未来支持动态 Java 插件，需要特别处理插件依赖隔离、类冲突、卸载和权限，不能简单把所有 jar 放到主 classpath。

### 65. Spring 声明式事务为什么有时会失效？

**参考答案：**

常见原因包括同类内部调用绕过代理、方法不是可代理的 public 方法、对象不是 Spring Bean、异常被 catch 后未继续抛出、抛出的异常不在回滚规则内，以及新线程中的操作不受原线程事务控制。

还要注意事务只覆盖同一个事务管理器控制的资源。MySQL 事务不能自动覆盖 Kafka、Redis、MinIO 或 Elasticsearch。IntelliDoc 的“数据库记录 + Kafka 事件”不能仅加一个 `@Transactional` 就认为强一致，应使用 Outbox、幂等消费和补偿机制。

定位时可以确认代理类型、事务拦截日志、传播行为和最终 SQL 提交情况，而不是反复添加注解。

### 66. 如何处理缓存穿透、击穿和雪崩？数据库与 Redis 如何保持一致？

**参考答案：**

穿透是请求不存在的数据，可使用参数校验、缓存空值或布隆过滤器；击穿是热点 key 过期时大量请求同时访问数据库，可用互斥重建、逻辑过期或提前刷新；雪崩是大量 key 同时过期或 Redis 故障，可给 TTL 加随机值、分层缓存、限流和降级。

数据库与缓存常采用 Cache Aside：读时缓存未命中查库再回填；写时先更新数据库，再删除缓存。删除失败要重试或通过消息/订阅 binlog 补偿。并发读写仍可能出现短暂不一致，强一致业务不能只依赖旁路缓存。

权限数据尤其要谨慎：宁可短暂拒绝合法访问，也不能因旧缓存放行越权访问，可以使用较短 TTL、权限版本号和敏感操作实时校验。

### 67. Nacos、Sentinel 和 Gateway 在微服务体系中分别做什么？

**参考答案：**

Nacos 常用于服务注册发现和配置管理；服务实例上报地址与健康状态，消费者通过服务名找到实例。配置中心让配置集中管理并支持动态更新，但密钥仍应使用专门的密钥系统。

Sentinel 提供流量控制、熔断降级和系统保护，可以按 QPS、并发线程、慢调用比例或异常比例定义规则。Gateway 位于入口，负责路由、鉴权、限流、灰度和跨域等通用能力。

它们不能替代业务层治理。网关鉴权后，下游敏感接口仍需校验权限；注册中心短暂不可用时客户端应利用本地缓存；限流规则要根据容量测试设置，不能随意填写阈值。

### 68. Ribbon 或客户端负载均衡的基本策略有哪些？如何处理实例故障？

**参考答案：**

常见策略包括轮询、随机、加权、最少连接和一致性哈希。客户端负载均衡从注册中心获取实例列表，在调用方选择目标，减少独立代理跳转，但每个客户端都要维护发现、健康和重试逻辑。较新的 Spring Cloud 通常使用 Spring Cloud LoadBalancer，回答时应说明 Ribbon 属于较早方案。

实例故障时要结合健康检查、超时、熔断和有限重试。重试只适合幂等请求，并应避免在多层同时重试造成请求放大。对于上传、创建等非幂等接口，应使用幂等键或禁止自动重试。

### 69. MinIO 中的大文件合并和下载如何避免占满 JVM 内存？

**参考答案：**

不能将全部分片读取到 `byte[]` 后拼接。应按顺序打开分片流，通过固定大小缓冲区写入目标流，或使用对象存储支持的 multipart compose 能力，让数据尽量在存储端合并。下载也应流式响应，并正确设置 Content-Length、Range、文件名和 Content-Type。

同时限制单请求并发分片数、总文件大小和超时，流必须在 finally 或 try-with-resources 中关闭。若使用预签名 URL，可以让客户端直传 MinIO，减少应用服务器带宽，但生成 URL 前后仍要做租户权限和对象 key 校验。

### 70. 线上接口突然变慢，你会怎样使用 Linux 和容器工具排查？

**参考答案：**

先确认影响范围和时间点，查看监控中的 QPS、错误率、P95/P99、CPU、内存、GC、线程、连接池和下游依赖。容器环境中同时检查 Pod 重启、CPU throttling、OOMKilled、资源 limit、节点状态和网络错误。

应用侧通过 Trace 定位慢在哪一段，再查看线程 dump 是否大量 BLOCKED/WAITING、数据库慢 SQL、Redis/Kafka/ES 延迟和 HTTP 连接池。CPU 高可用 async-profiler 或 JFR，内存异常看 GC 日志和 heap dump，网络问题查看连接与超时。

排查过程中先止损，例如限流、扩容、关闭高成本功能或降级；保留证据后再修复根因，避免直接重启导致现场丢失。

## 六、系统设计、测试与工程化

### 71. 如何为 Sidekick 设计测试体系？LLM 输出不稳定时怎么测试？

**参考答案：**

我会分层测试。纯逻辑层测试计划解析、拓扑调度、记忆排序、路径校验、命令拒绝、消息协议和切片；模型客户端用 MockWebServer 模拟 SSE、工具分片、超时和错误码；工具层用临时目录和伪执行器验证副作用；MCP 用内存 Transport 测 JSON-RPC 请求响应匹配。

Agent 测试不直接依赖真实模型，而是使用可编程 Fake LlmClient，预设“第一次返回工具调用、第二次返回答案”，验证消息序列和退出行为。端到端评测再调用真实模型，允许结果文本变化，但检查任务是否完成、文件是否正确、测试是否通过、调用成本和轮数是否在范围内。

当前仓库已有较多单元测试，下一步应补充固定任务集和跨模型回归，区分确定性单测与概率性评测。

### 72. 如果线上发现 Agent 修改了错误文件，你如何定位？

**参考答案：**

先停止后续执行，保留现场并使用快照比较变更。通过 run ID 串联用户输入、组装后的 Prompt 摘要、模型响应、工具名称、规范化参数、审批结果、文件 diff 和时间线，确认错误来自用户意图理解、代码检索、模型决策、工具参数还是并发冲突。

如果是检索召回错误，应检查候选列表与分数；如果模型选择错误文件，要看 Prompt 是否提供了足够路径信息；如果工具层写错，则检查路径规范化和工作目录。恢复后补充最小复现、回归测试和安全规则。

日志要脱敏，不能记录完整 API Key、用户隐私文档或不必要的源码全文。

### 73. 如何衡量一个 RAG 系统的效果？

**参考答案：**

应拆成检索和生成两层。检索层使用标注问题与相关片段，评估 Recall@K、Precision@K、MRR、NDCG，并按文档类型、租户和问题类别切分。生成层评估答案正确性、完整性、引用一致性、幻觉率和拒答质量。

线上还要观察 P50/P95 延迟、Embedding 和 LLM 成本、无结果率、降级率、用户追问率和人工反馈。A/B 测试混合检索权重、chunk 大小和 top K 时要固定评测集，避免只凭个别案例。

权限正确性是独立的硬指标：任何越权召回都不能被平均准确率掩盖。

### 74. 如果 IntelliDoc 的索引量增长到亿级，你会怎样扩展？

**参考答案：**

首先按租户规模和访问模式设计索引，而不是简单每租户一个索引导致小索引爆炸。可以按业务域或时间分索引，用 routing 让同一租户落到固定 shard，并通过 alias 管理版本。

其次控制 shard 大小、映射字段和向量维度，冷热分层旧文档，批量写入并调整 refresh interval。KNN 查询要限制租户过滤范围、合理设置 candidate 数，并根据成本考虑量化或降维。

处理链路通过 Kafka 分区和无状态 Worker 横向扩容，Embedding 做批处理、限流和缓存。最后必须基于容量测试决定节点、分片和副本，不能给出脱离数据规模的固定参数。

### 75. 你在项目中遇到过最难的问题是什么？如何回答才可信？

**参考答案：**

可以选择一个自己确实调试过的问题，例如流式 Function Calling 的参数被拆成多个 SSE chunk。回答按 STAR 组织：背景是模型在一次响应中返回多个工具调用；问题是直接解析单个 chunk 导致 JSON 不完整或调用串位；我的任务是保证流式显示和工具协议正确。

我通过记录原始事件，确认函数名、参数和多个 tool index 会交错增量返回；随后为每个调用维护累加器，在 `[DONE]` 后统一构造 ToolCall，并通过 tool_call_id 绑定结果。最后使用 MockWebServer 构造随机切分和多工具响应做回归测试。

回答中应讲清观察到的现象、错误假设、验证手段和代码改动。不要只说“查资料后解决了”，也不要编造性能提升数字。

## 七、HR 与综合素质问题

### 76. 你为什么应聘 Java 后端，而不是只做大模型应用？

**参考答案：**

我对大模型应用感兴趣，但我认为可靠的 AI 产品最终仍依赖扎实的后端工程。模型调用只是链路的一部分，真正落地还涉及权限、并发、存储、消息一致性、故障恢复、成本和可观测性。

Java 生态在企业系统、微服务和中间件方面成熟，适合我把 AI 能力与后端工程结合。我的目标不是只会写 Prompt，而是能够把不稳定的模型能力封装成稳定、可维护的业务服务。

### 77. 你是独立开发，如何证明项目不是简单跟着教程做的？

**参考答案：**

我可以从设计取舍和失败案例证明。例如 Sidekick 中为什么简单任务用 ReAct、复杂任务用 DAG；为什么工具结果必须按 call ID 回填；为什么历史压缩要保留工具消息原子性；为什么本地 CLI 选择 SQLite 而不是独立向量数据库。这些决策都与具体场景有关。

我也能打开代码说明核心类的职责、一次请求的调用链、相应测试和仍存在的问题。如果只是照教程，很难解释边界条件、替代方案和后续改进。我不会把没有实现的能力说成已完成，也不会编造用户规模或性能数据。

### 78. 团队合作经验较少，你如何快速融入团队？

**参考答案：**

独立开发让我具备从问题定位到交付的完整意识，但我也知道团队开发更强调沟通和约定。我会先理解现有架构、编码规范、发布流程和业务目标，从小任务开始提交可审查的改动。

遇到问题时，我会先自行复现、阅读代码和文档，再带着现象、日志、已尝试方案和具体疑问请教，而不是只说“不会”。提交前补测试、自查 diff，及时同步风险和进度，并接受评审意见。

### 79. 你如何看待使用 AI 辅助编程？

**参考答案：**

AI 能提高代码检索、样板代码、测试生成和问题分析效率，但不能替代开发者对需求、架构、安全和结果的责任。我使用 AI 时会给出明确上下文和验收条件，对生成代码逐行审查，并通过测试、静态分析和实际运行验证。

涉及公司代码、密钥和用户数据时，要遵守数据安全规则，不能随意发送到外部模型。对于数据库变更、权限和生产操作，必须保留人工审批。AI 是提高效率的工具，不是把错误责任转移给模型的理由。

### 80. 如果拿到一个完全不熟悉的任务，你会如何推进？

**参考答案：**

我会先确认目标、边界和验收标准，把未知问题拆成业务未知、技术未知和环境未知。然后从入口、数据模型、调用链和已有测试开始阅读，构造最小复现，先验证关键假设。

方案确定后，我会拆成小步骤，优先完成可验证的最小闭环，再补异常处理、测试和文档。如果发现需求存在重大歧义或方案会产生不可逆影响，会尽早向负责人确认。过程中持续记录结论和风险，避免长时间闭门开发后才发现方向错误。

## 九、准备重点与风险提示

1. **最优先准备 Sidekick 源码。** 至少能从 `Main → Agent/PlanExecuteAgent/AgentOrchestrator → LlmClient → ToolRegistry` 讲清完整调用链。
2. **IntelliDoc 必须准备实现证据。** 当前提供的仓库是 Sidekick，无法从代码验证 IntelliDoc。面试时要准备 IntelliDoc 仓库、接口、表结构、ES mapping、Kafka 消息结构或运行截图。
3. **不要虚构性能指标。** 简历目前没有给出 QPS、P95、数据量和准确率。可以说“尚未做系统压测，这是下一步”，比编数字更可信。
4. **不要把 RBAC 与 ABAC 混为一谈。** 角色是 RBAC；组织、文档属性和标签参与判断时已经带有 ABAC 特征。
5. **不要声称本地 Agent 是强沙箱。** 当前更准确的表达是 HITL、路径校验、命令检查、审计和快照组成的安全执行边界。
6. **准备一个真实故障案例。** 推荐从 SSE 工具调用拼接、上下文压缩、DAG 依赖或大文件合并中选择，讲清复现、定位、修复和测试。
